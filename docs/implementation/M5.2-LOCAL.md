# M5.2 — Local Runtime Planning Brief

## Scope and release gate

Implement the [roadmap local-runtime slice](ROADMAP.md#m52--local-runtime-connectors) for Ollama, vLLM and llama.cpp. Reuse compatible Responses endpoints first. A new native API Connector or Responses-to-Chat translator is justified only by pinned research and separately scoped implementation; no universal LLM model or new client Adapter is part of this plan.

This is planning, not evidence of implementation or runtime/model availability. [TASKS](TASKS.md#m52--local-runtime-connectors) owns status/dependencies. Normal checks require neither models, GPUs, containers nor external calls. Each runtime is accepted independently only after versioned fixtures, an evidence-scoped capability matrix and reviewed reproducible direct/gateway observations. Full M5.2 completion needs all three or a separate explicitly accepted scope decision.

### Ollama source pin and Responses findings (reviewed 2026-10-11)

**Versioned source baseline:** official [`ollama/ollama` v0.40.3 release](https://github.com/ollama/ollama/releases/tag/v0.40.3), published 2026-10-11; tag resolves to commit [`eab97e9f92b9a25c2d52d2cc6c1b1c99bd9fae21`](https://github.com/ollama/ollama/commit/eab97e9f92b9a25c2d52d2cc6c1b1c99bd9fae21). Pin is source research, not a claim about an installed runtime. The [official compatibility guide](https://docs.ollama.com/api/openai-compatibility) identifies `POST /v1/responses` (added v0.13.3), streaming, function tools and reasoning summaries as supported and expressly excludes `previous_response_id` and `conversation`. The versioned [route](https://github.com/ollama/ollama/blob/eab97e9f92b9a25c2d52d2cc6c1b1c99bd9fae21/server/routes.go#L2342) passes `/v1/responses` through Responses middleware into Chat; [request mapping](https://github.com/ollama/ollama/blob/eab97e9f92b9a25c2d52d2cc6c1b1c99bd9fae21/openai/responses.go#L504-L555) and [conversion](https://github.com/ollama/ollama/blob/eab97e9f92b9a25c2d52d2cc6c1b1c99bd9fae21/openai/responses.go#L557-L818) confirm the boundary.

**Scope and request semantics:** target for local inference is `http://localhost:11434/v1/responses`. Docs demonstrate model names (example `qwen3:8b`); there is no API-wide fixed model or template in this release. Actual tool/reasoning behavior therefore remains model/template-specific and **Unknown** until tested with a named model digest and its Modelfile/template. Documented accepted request fields: `model`, `input`, `instructions`, `tools`, `stream`, `temperature`, `top_p`, `max_output_tokens`, `reasoning.effort`, and Ollama extension `think`. Docs describe `previous_response_id` and `conversation` as unsupported state. In the pinned request struct, `conversation` is decoded but not consumed by conversion; `previous_response_id` has no request field, and `tool_choice` has only an unsupported comment (no request field/validation). Thus state/tool-choice semantics are unsupported, but whether requests reject, ignore, or otherwise handle these JSON properties is **Unknown**; do not assert rejection without a direct observation. Source comments mark `background` unsupported and `include` ignored; `truncation` is explicitly unchecked. Decoder accepts input string or supported item-array types; an unrecognized item type returns a parse error. Local docs/source establish `function` tool declarations/calls and source handles namespace-wrapped functions. They do not establish support for OpenAI `custom`/freeform tools; the compatibility guide explicitly excludes custom/freeform call replay for cloud, which is a separate endpoint and not evidence about local behavior. Other undocumented fields and local custom-tool behavior should be treated as **Unknown**, not assumed accepted or rejected.

**Auth and outputs:** official [authentication docs](https://docs.ollama.com/api/authentication) say local API requires no authentication; the [compatibility guide](https://docs.ollama.com/api/openai-compatibility#local-server-usage) says an OpenAI SDK requires an API-key value but local Ollama ignores it (`ollama` is the example). This differs from direct `ollama.com/v1`, which requires bearer API key; do not apply local behavior to cloud. Source emits SSE event/data frames and flushes each frame; normal stream completion is `response.completed` with usage ([writer and middleware](https://github.com/ollama/ollama/blob/eab97e9f92b9a25c2d52d2cc6c1b1c99bd9fae21/middleware/openai.go#L492-L549), [completion event and usage](https://github.com/ollama/ollama/blob/eab97e9f92b9a25c2d52d2cc6c1b1c99bd9fae21/openai/responses.go#L1988-L2004)). `response.failed` is evidenced only for streaming web-search failures handled by `WebSearchResponsesWriter.writeWebSearchError` ([source](https://github.com/ollama/ollama/blob/eab97e9f92b9a25c2d52d2cc6c1b1c99bd9fae21/middleware/openai.go#L1109-L1156)); ordinary `BaseWriter.writeError` returns a JSON error ([source](https://github.com/ollama/ollama/blob/eab97e9f92b9a25c2d52d2cc6c1b1c99bd9fae21/middleware/openai.go#L65-L78)). Ordinary streaming inference-error terminal behavior is **Unknown**; no general `response.failed` guarantee is claimed. On normal completion, prompt/eval counts map to `input_tokens`/`output_tokens`, `total_tokens` is their sum, cached prompt count maps to cached detail, and `reasoning_tokens` is reported as 0; true reasoning-token accounting remains **Unknown**. The client must resend conversation history in `input` each turn; server-side history/session continuity is not offered. Source semantics do not establish runtime wire behavior for a particular model.

**Fixture and later live-probe scope:** M5.2-010 synthetic fixtures should pin this release SHA and a declared fake model/template profile; cover stateless string and item-array text requests, function declaration/call/output with stable call ID and client-resubmitted history, `include`'s documented ignored status, and source-derived unsupported/unused fields without assuming they are rejected. Assert parse failure for an unknown input-item type, where pinned source explicitly errors. Cover basic request/response fields and normal ordered SSE (first delta before terminal, `response.completed`, usage counts/details). Test web-search `response.failed` only as that special path if included; do not require `response.failed` for ordinary streaming inference errors, whose terminal behavior is **Unknown**. Assert ignored/unknown usage policy rather than equating missing metrics with zero. No generated model behavior is implied by synthetic source-derived fixtures. M5.2-024 direct/gateway observation is limited to an operator-provisioned local Ollama v0.40.3 at localhost, exact model digest and template, one bounded stateless text JSON/SSE request, and—only if the model actually emits one—a function call and caller-executed result resubmission; record observed state/tool-choice handling, auth mode and event/usage semantics. Do not probe cloud, native `/api/chat` or `/completion`, stateful continuation, custom tools, unpinned aliases, or infer compute cancellation. Text/tools/template-specific capabilities, state/tool-choice runtime handling, ordinary error terminals, cancellation propagation, real terminal/usage behavior and direct-vs-gateway equivalence stay **Unknown** until reviewed runtime evidence exists.

### vLLM source pin and Responses findings (reviewed 2026-10-11)

**Versioned source baseline:** official [`vllm-project/vllm` v0.31.0 release](https://github.com/vllm-project/vllm/releases/tag/v0.31.0), published 2026-10-05, points to commit [`db9527a46873454610df6dbedf79a36d6bf1a7f6`](https://github.com/vllm-project/vllm/commit/db9527a46873454610df6dbedf79a36d6bf1a7f6). This is the source-audit pin, not an installed binary, model, or live compatibility claim. Versioned [OpenAI-compatible server docs](https://docs.vllm.ai/en/v0.31.0/serving/online_serving/openai_compatible_server/) advertise `POST /v1/responses` for text-generation models and related response retrieval/cancel routes. The tag's [Responses request model](https://github.com/vllm-project/vllm/blob/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/entrypoints/openai/responses/protocol.py) and [serving implementation](https://github.com/vllm-project/vllm/blob/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/entrypoints/openai/responses/serving.py) provide source-level support only; gateway transport (HTTP path, opaque bytes, SSE delivery/cancel) is independent from model rendering and parsing.

**Endpoint, launch and model/parser requirements:** start the documented server with `vllm serve <model>`; pin model and its exact repository revision/digest separately. Network/bind settings such as `--host`/`--port` and optional auth are server choices, not Responses semantics. Responses rendering is text-generation-only and uses the selected model tokenizer/renderer; docs/source do not establish a model-independent template or all-model support. `--chat-template`/template kwargs can affect prompt formatting. Function/tool output is model-dependent: source constructs `ParserManager` with configured `--tool-call-parser`/`--enable-auto-tool-choice` (and optional `--reasoning-parser`), so parser availability/configuration and model output format are separate prerequisites, not gateway transport. Parser names and appropriate template are model-specific; whether a particular model reliably emits parseable function calls remains **Unknown** absent a named-model probe. Server-managed `ToolServer` can execute requested built-ins/MCP in its own loop and is expressly excluded from the gateway slice.

**Request semantics (tag's `ResponsesRequest`):** core API fields modeled include `background`, `include`, `input` (string or item list), `instructions`, `max_output_tokens`, `metadata`, `model`, `parallel_tool_calls`, `previous_response_id`, `reasoning`, `store`, `stream`, `temperature`, `text`, `tool_choice`, `tools`, `top_logprobs`, `top_p`, `truncation`, and `user` (plus typed documented fields). Schema validation determines accepted types; it is not evidence every OpenAI semantic is honored. Source explicitly rejects non-null `prompt`. `prompt_cache_key` is an optional `str` field in the pinned request model; its source comment explicitly says it is not implemented and vLLM will ignore it, so classify it as **accepted-but-ignored**, not unsupported or unknown. With storage disabled (default), `store` is silently turned off; `background` requires storage and otherwise fails validation. `previous_response_id`, response retrieval, and cancellation depend on in-process `response_store`; no durable/cross-restart session guarantee. `previous_input_messages` is an implementation-specific alternative and cannot accompany `previous_response_id`. vLLM additions include `watermarking`, `request_id`, `session_id`, `priority`, cache/media/model-processor kwargs and `vllm_xargs`; do not forward or claim these as portable OpenAI fields. Chat-only `messages`, Chat `user`-ignored behavior and chat parallel-tool semantics are not evidence for Responses. Unknown extra JSON-field handling and runtime behavior outside pinned schema/docs remain **Unknown**; no broad accept/ignore/reject claim is inferred.

**Auth, output and usage:** vLLM docs show optional `--api-key` / `VLLM_API_KEY`; when configured bearer auth applies to `/v1` (including Responses), while absent configuration means no API-key enforcement. It is server-side shared key auth, not account-scoped provider auth. Docs warn it does not secure every server route, so bind to a trusted interface/firewall and do not expose the server merely because this route is protected. Normal Responses output includes input/output/total token counts; source derives prompt/generated counts from engine context, cached-token detail from engine metrics, per-turn counts and reasoning detail (parser/context-dependent), with tool-output tokens not necessarily fully accounted in every parser mode (TODO remains). Treat each usage subfield as source-reported, not proof of independent billed-token parity. Source has typed `response.completed` and emits ordered Responses lifecycle/delta events; terminal behavior for every generation/engine failure and exact SSE bytes/error path is **Unknown** until fixture/runtime tests. Cancellation of request transport is not proof of engine compute cancellation.

**Fixture and later direct-probe scope:** M5.2-010 synthetic trace/fixtures should pin this SHA and label all data synthetic; use deterministic fake model/template/parser outputs. Cover text input in string and item-list form, basic JSON response, streaming ordered created/in-progress/item/text-delta/item-done/completed lifecycle, usage counts/details as emitted, client-owned history resubmitted on the next request, source-backed prompt rejection/default store behavior, and `prompt_cache_key` accepted by the request schema but ignored with no prompt-cache effect. Keep unknown extra-field handling explicitly **Unknown**. Include function-call parse/call/result only as a synthetic model+chat-template+tool-parser-specific trace, separating caller-executed tools from vLLM's built-in server tool loop. Add API-key configured and absent header cases at route level; avoid testing unprotected ancillary routes as if secured. Do not require cross-restart retrieval, background/session persistence, model-independent tools/reasoning, or a particular error terminal. M5.2-025 direct probe, only once explicitly provisioned: one local vLLM v0.31.0 server with exact model revision, template and parser configuration, one bounded stateless text JSON request and one SSE request; verify bearer-key enforcement (configured), first event before completion, order/terminal, input/output usage and client-resubmitted history. Attempt a function call only if the named model/parser profile is in scope and record actual output, never require stochastic generation. No GPU/runtime install/download is authorized here. Hardware footprint, exact platform/model fit, actual field handling, model/tool/reasoning quality, error/cancel behavior, usage parity and gateway equivalence remain **Unknown** pending separately provisioned evidence.

### llama.cpp source pin and Responses findings (reviewed 2026-10-11)

**Versioned source baseline:** official [`ggml-org/llama.cpp` v0.6.0 release](https://github.com/ggml-org/llama.cpp/releases/tag/v0.6.0), published 2026-10-05. The annotated [`v0.6.0` tag object](https://api.github.com/repos/ggml-org/llama.cpp/git/tags/69ecae922d2b60c1fa8c590279f4e2099af75111) resolves to source commit [`d81235049384534c167caea52b85a694f6103d14`](https://github.com/ggml-org/llama.cpp/commit/d81235049384534c167caea52b85a694f6103d14). This is an official source pin, not evidence of a local build, installed server, model or live compatibility.

**Endpoint and internal boundary:** the versioned [server README](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/tools/server/README.md#L1489-L1530) documents `POST /v1/responses` as OpenAI-compatible and explicitly says it converts Responses input to Chat Completions. The [route handler](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/tools/server/server-context.cpp#L5343-L5358) calls `server_chat_convert_responses_to_chatcmpl` internally before invoking Chat handling. This backend conversion is not gateway translation: the gateway must preserve admitted native request/response bytes and streaming semantics; no gateway conversion is licensed by this source finding.

**Field behavior in the pinned converter:** `input` is required; string and item-array inputs are recognized. A non-empty `previous_response_id` is explicitly rejected, so callers own history and must resend prior items. `instructions` becomes a system message; input text/image, prior assistant messages, function calls/outputs, and first reasoning summary content are mapped into Chat messages. `input_file` and unrecognized item forms/types throw; missing required text/image/tool-output members throw. Function tools are mapped to Chat function tools (converter inserts `strict: true` if absent); non-function Responses tools are warned about and skipped rather than rejected. `max_output_tokens` maps to `max_tokens`; `reasoning.effort` maps to `reasoning_effort` (only that reasoning member is handled here). The converter begins with a copy of the request and leaves other fields in place; this alone does not establish whether the downstream Chat parser accepts, ignores or rejects every Responses field. Do not claim general field parity: fields such as `store`, `background`, `metadata`, `include`, `text`, `tool_choice`, `parallel_tool_calls`, and unknown extensions are **Unknown** absent deeper parser proof or direct probe. Source evidence is from [server-chat.cpp](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/tools/server/server-chat.cpp#L6-L312); endpoint registration is in [server.cpp](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/tools/server/server.cpp#L263-L297).

**Launch/model/template/tool constraints:** the versioned [server README options](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/tools/server/README.md#L192-L194) set the default listen host to `127.0.0.1` and `--port` to `8080`; its [quickstart](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/tools/server/README.md#L441-L446) confirms `127.0.0.1:8080`. Thus the default Responses base URL is `http://127.0.0.1:8080/v1/responses` (SDK base URL `http://127.0.0.1:8080/v1`); an explicitly configured `--port`/`LLAMA_ARG_PORT` overrides it and must be recorded for any probe. The README documents `llama-server -m <GGUF>` (or a model repository/file option), Jinja enabled by default, and model-metadata chat template by default; `--chat-template`/`--chat-template-file` override the template ([options](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/tools/server/README.md#L228-L240)). OpenAI-style function calling requires `--jinja` and may require a compatible model-specific template override ([function-calling docs](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/tools/server/README.md#L1408-L1422)). Tool calls, parallel calls and reasoning are model/template-dependent, not guaranteed by the endpoint. No exact model/GGUF digest, template, parser success, CPU/GPU/RAM fit, throughput or device is selected; these remain **Unknown** and must be explicitly provisioned/pinned for real evidence.

**Authentication, stream and usage:** `--api-key` defaults to none; source docs its `LLAMA_API_KEY` environment counterpart. The [HTTP auth middleware](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/tools/server/server-http.cpp#L260-L290) skips key checks when no keys are configured; otherwise it checks Authorization (stripping an optional `Bearer ` prefix), with X-Api-Key also accepted. Therefore use bearer auth when configured, and do not confuse an SDK placeholder key with enforced auth. The [Responses serializer](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/tools/server/server-task.cpp#L1166-L1279) emits ordered `response.created`/`response.in_progress`, item/text/reasoning/function deltas; final response code emits `response.completed` with output items and usage. [SSE formatting](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/tools/server/server-common.cpp#L1704-L1719) uses `event: <name>`, `data: <JSON>`, and a blank line between events. Normal completion reports prompt tokens as `input_tokens`, decoded tokens as `output_tokens`, their sum as `total_tokens`, and cached prompt tokens in input details ([completion usage source](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/tools/server/server-task.cpp#L689-L706)). This is server-reported usage, not proof of independent billing/tokenizer parity. Error-terminal event behavior, disconnect-to-compute cancellation and wire behavior with a specific model are **Unknown**.

**Fixture and later direct-probe scope:** M5.2-010 synthetic fixtures should pin this SHA, label fixtures synthetic, and use deterministic fake template/model outputs. Cover request `input` string and item list, explicit unsupported `previous_response_id`/`input_file` and invalid item errors, instruction and max-output/reasoning mappings, function declaration/call/result and client-resubmitted history, ignored non-function tools, plus an explicit Unknown-field policy instead of invented support. Assert the `/v1/responses` route path and SSE event/data framing (do not bake a server port into synthetic loopback fixtures), first incremental event before completion, order and `response.completed`; verify prompt/decode/total/cached usage mapping. Do not assert stochastic generation, error terminal form, actual tool correctness, compute cancellation or GPU performance. M5.2-026, only after separate operator provisioning and exact command/bounds in its own READY card, should compare one local v0.6.0 server and gateway for a bounded stateless text JSON request and SSE request with same pinned GGUF digest/template and auth setup. Default direct endpoint is `http://127.0.0.1:8080/v1/responses`; record the actual address and any port override. Compare first-event timing, event framing/order/terminal, usage and resubmitted history; attempt a function-call cycle only if that exact model/template emits a call. No install, build, model download, daemon or inference was performed in this source task.

## Decision gates

005 defines per-runtime allowed/rejected/unknown semantics. 006 selects reuse versus one minimal compatible implementation and checks optional configuration/auth methods, exact model/capability declarations and transport observer seams. It must not create a profile registry framework or commit hypothetical interfaces. If research exposes distinct native/translation work, re-scope and split 008–013 before READY rather than implementing the whole branch speculatively. A semantic contract change needs an ADR and synchronized specification first.

Native mode preserves admitted request and response bytes, including allowed unknown extensions. Injected defaults, model rewriting or converted provider bodies require declared translation mode. Significant unsupported semantics reject before provider dispatch in the Connector. Core never parses provider JSON/SSE/reasoning/tools. Only supported exact scopes satisfy requirements; fixture/localhost identity cannot promote production capabilities. Unknown/absent usage is not zero, and unknown estimates use existing rejection/conservative reservation policy.

Local no-auth must be explicit and omit upstream Authorization, never fabricate a secret or disable client auth. Bearer uses selected scoped runtime credentials. No connector-owned persistence or automatic provider/host auth inference. Existing native behavior stays backward compatible.
