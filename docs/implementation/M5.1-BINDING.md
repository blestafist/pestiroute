The v2 `headless` flow starts at `/api/accounts/deviceauth/usercode`, displays
the returned user code at `https://auth.openai.com/codex/device`, polls
`/api/accounts/deviceauth/token`, then exchanges returned authorization code
and verifier at `/oauth/token`. It is not RFC 8628's direct device-code token
exchange. OAuth access token becomes a Bearer token and selected account
metadata supplies `ChatGPT-Account-Id`; inbound client account/auth headers are
not selection authority. For a text paper trace, an OpenCode Responses request
containing a user `input` item and `stream:true` is sent to the profile endpoint
with that scoped bearer/account header; upstream SSE `data:` events are forwarded
as original bytes and terminal/usage information is observed separately. This
trace selects transport shape only, not authorization, successful inference or
account entitlement.

Runnable client selection is **OpenCode V2 CLI 2.0.6**, distinct from the
research source revision above. The 2.0.6 source tag is pinned in the table;
the [M1 client setup](REFERENCES.md#m1-compatibility-baseline) and retained
live evidence concern OpenAI **public API** Responses only, not ChatGPT
subscription OAuth. Thus 2.0.6 satisfies the identifiable runnable-client
selection, but its behavior against this Codex profile remains unverified. The
installed `/usr/bin/opencode` here is 2.0.21; no 2.0.6 executable was run in
this task.

## Device-auth user action (DEC-009)

DEC-009 adds optional `AuthResult.UserAction *AuthUserAction`, where the
provider-neutral value is `{VerificationURI string, UserCode string,
PollInterval time.Duration}`. Core projects it to transient
`AuthSession.UserAction` for the admin caller; it is not persisted. Presence is
self-describing (`nil` means no action), allowing older producers to omit it
and older consumers to ignore it. It is only an operator-presentation
projection; do not encode it into `State`, print Connector state, or let the
Connector write directly to the operator. The Connector extracts only the safe
action from the provider response and never includes a device-auth identifier,
PKCE verifier/challenge, access/refresh token, or arbitrary raw response/state.
Core validates before exposure: `VerificationURI` is 1–2048 printable ASCII
bytes without spaces/control bytes, absolute HTTPS with host and no userinfo;
`UserCode` is 1–256 printable ASCII bytes without controls; `PollInterval` is
positive. URI/code must not contain authentication secrets. The operator opens
the URI and enters the code; no
browser callback, secret-bearing URL, or agent-side browser automation is
implied.

`start` invokes Authenticate once. A supported result with `NextAction=continue`
creates the existing opaque, encrypted session with a runtime-fixed
`ExpiresAt`; the safe projection is returned for presentation. An action has a
positive provider poll interval. Each explicit
`continue --session` performs at most one poll, and a pending result returns the
next safe projection and provider poll interval. The caller waits at least that
interval before requesting another poll; no coordinator/admin infinite polling
loop is permitted. Polling never moves the fixed expiry. A result with no
continuation completes the flow and persists credentials only under the
existing acknowledged atomic credential-write rule.

`UserAction` is allowed only on `Supported=true, NextAction=continue`; it is
invalid on completed, unsupported, or refresh results. A nil action with
`continue` is a valid legacy opaque continuation needing no operator input, not
an invalid/malformed result. A Connector flow that does require user
interaction MUST return a valid action; its auth-flow conformance tests enforce
this obligation because Core cannot infer a missing presentation value from
opaque state. Presence/nil is the explicit optional-result discovery mechanism;
no new capability is introduced. If an action is malformed or inconsistent,
Core discards every result field before exposure/persistence. Start creates no
session; Continue consumes its already-claimed state/claim; an invoked Refresh
result is discarded and its marker quarantined. If consuming a Continue claim
cannot be committed, no result is exposed and DEC-007 restart recovery remains
the fail-closed backstop.

Cancellation is caller-context cancellation, not a provider action: before a
continuation call it consumes the session; after invocation begins it consumes
the claimed continuation conservatively because provider state may have been
used. The durable DEC-007 claim remains the single-winner authority; neither a
presentation value nor the caller's session handle grants claim ownership.
Expiry is checked before every continuation and cannot be extended by a
provider response. Admin output is limited to the safe URI/code, poll interval,
opaque runtime session handle, and runtime expiry; never serialize or log the
opaque state or credentials.

DEC-009 accepts this additive v1 semantic extension: existing Connectors may
omit the optional field; a Connector flow requiring operator interaction must
return it. The extension adds no operation, provider branch, persistence field,
or state-lifetime change. Older producers remain valid with a nil action and
older consumers may ignore the field. CONTRACT and M3-AUTH are synchronized;
implementations must preserve the distinct presentation/opaque-state boundary.
