the returned user code at `https://auth.openai.com/codex/device`, polls

account entitlement.

## Request, stream, and retry binding (M5.1-004)

### Dialect and field policy

The first profile is **standard, non-Lite Responses over HTTP/SSE**. Lite's
prefix-item layout and forced parallel-call behavior are a different dialect;
never infer or select it from a model name. Native mode accepts only a validated
request already satisfying this profile and sends its admitted body byte-for-byte.
It cannot add `store:false`, replace a model, or remove fields. Explicit
Responses-to-Codex translation is a distinct, configured mode: it may construct
a new body but leaves the admitted envelope immutable, rejects duplicate keys,
and preserves unrecognized fields/values unless they have known-unsupported
semantics. Neither mode may silently weaken a client request.

| Field / feature | Profile policy |
| --- | --- |
| `model`, `input`, `instructions` | Route by the exact configured model; preserve chronological input, all item/part IDs, call IDs, order, extensions, and existing instructions. No message reconstruction or movement of later instructions. |
| `stream` | Streaming is required. Explicit `false` is `unsupported_feature` before send. Translation may set `true`; native mode does not rewrite it. |
| `store` | The backend request must use `false`. Translation supplies `false` when omitted and rejects explicit `true`; native mode requires explicit `false` because it cannot impose the policy by rewriting bytes. |
| `include`, `reasoning`, encrypted reasoning | Preserve explicit supported values and the whole reasoning item/ciphertext. Translation may add `reasoning.encrypted_content` only as a documented profile default. Never decrypt, log, strip, or replace ciphertext with summary text. |
| `tools`, `tool_choice`, `parallel_tool_calls` | Ordinary function tools and only fixture-verified choices are supported. Preserve explicit parallel choice; a required parallel capability must be admitted as `llm.tools.parallel` or rejected before send, never changed to `false`. No hosted tool execution. |
| `max_output_tokens`, temperature, top-p, penalties, structured output | Preserve only when the selected profile verifies support. A meaningful unsupported explicit value is rejected before send, never dropped. An omitted output cap remains omitted; it is not an estimate or a promise of bounded output. |
| `background`, Lite-only fields, compaction, unsupported modalities/namespaces | Reject requests that require unsupported behavior; do not downgrade to foreground, Lite, compaction, or a narrower tool set. Unknown optional extensions may pass untouched only where the selected profile permits ignoring them; unknown required semantics fail closed. |
| `previous_response_id`, `conversation` | Treat as account/deployment-bound state. Until a separately accepted continuation binding exists, reject these controls rather than pretending that full-history replay or cache affinity makes a response resource portable. Full-history reasoning/tool replay without these controls remains supported on its pinned target. |

Decode validates what it owns, including duplicate JSON keys and declared
capabilities; Connector validates provider-profile semantics before network
send. Neither lets Core parse the body. The configured selected-account
credential supplies bearer auth and `ChatGPT-Account-Id`; inbound account,
organization, project, authorization, session, and auth headers never select
credentials or trusted affinity. Do not forward these selectors upstream.
`prompt_cache_key`, if present, is opaque cache metadata, not routing authority:
accept only a bounded non-empty printable ASCII value of at most 256 bytes,
preserve it without deriving it from a gateway request/attempt ID, and scope any
connector-local mapping to the selected account and profile. It does not grant
resource ownership or cross-target portability. Do not synthesize `session-id`
from a client header in this initial profile.

### Finite limits and deadlines

The v1 ingress limits remain operator-configured and enforced before admission;
the Codex profile's binding ceiling is **1 MiB request body and 16 KiB
aggregate request-header bytes**. Lower configured limits win. Connector
responses are read incrementally in at most **4 KiB Body frames**. Bound one SSE
event to **1 MiB**, a non-2xx diagnostic body to **64 KiB**, and aggregate
upstream response bytes to **64 MiB**; exceeding a bound ends the attempt as
incomplete/failed, never as a successful truncated response. These are profile
ceilings, not claims that existing M4 limits enforce each Codex-specific bound;
their enforcement and boundary regressions belong to the implementing cards.
No whole response or unbounded telemetry queue is permitted.

Apply separate finite phases: TCP connect **2 s**, TLS handshake **2 s**,
response headers **30 s**, stream idle **120 s**, and total request deadline
**30 min** from initial admission including all runtime-owned attempts. Cancellation
and the total deadline close the upstream body and propagate through the stream.
An idle/total timeout after Head is committed yields an incomplete attempt, not
a replacement response. Runtime configuration may tighten these ceilings but
must not make any phase or total deadline unbounded; streaming is not subject to
a short whole-client HTTP timeout.

### Affinity, outcomes, and retry

Account, connector instance, model, and profile are selected by trusted route
configuration, never by client headers. Opaque encrypted reasoning and
full-history tool continuations are pinned to that exact account/profile.
Known stateful or unknown affinity is eligible only on an effective singleton
target, following [M3's fail-closed affinity rule](M3-CONFIG.md#stateful-and-unknown-affinity);
this initial profile has no affinity directory and cannot reduce a multi-target
route from client cache metadata. A singleton permits the one execution only;
it does not authorize retrying that target or moving the request elsewhere.

One `Execute` sends at most one inference request. There is no internal retry,
redirect following, 401 refresh-and-replay, WebSocket/HTTP recovery, or hidden
idempotency assumption. Resolve/refresh credentials before Execute through the
runtime auth path. Local validation failures are non-retryable. Only confirmed
no-send evidence or a profile-verified explicit rejection before execution can
be classified `Retryable=true, RetryDisposition=safe`; a status code alone is
not evidence. DNS/connect failures qualify only when transport evidence proves
no request bytes could have been delivered. Any write failure after sending may
have begun, client cancellation after dispatch, or lost/uncertain acknowledgement
is unknown/unsafe and ends without replay. After Head is forwarded, any SSE
`failed`/`error`, `incomplete`, malformed/truncated stream, idle timeout, or EOF
without a recognized terminal event ends this committed attempt; it can never
fall back. Map `response.completed` to succeeded, `response.incomplete` to
incomplete, `response.failed`/`error` to failed, and EOF without a valid terminal
to incomplete. A non-2xx HTTP body is bounded and classified before Head; retain
client-visible bytes separately from sanitized `GatewayError` metadata.

Usage uses inclusive input/output totals; cached/reasoning counters are subsets,
not added again. Normal terminal usage is provider-reported; absent usage is
unknown, and usage observed before interruption is partial rather than zero.
Quota headers/events are not token usage. Every path finalizes attempt,
reservation, and request closure exactly once under the
[v1 error/usage contract](CONTRACT.md#error-model).

Paper checks: an explicit unsupported output limit or requested parallel mode
is rejected before upstream contact; `store:true` is rejected and cannot be
silently rewritten in native mode; encrypted reasoning plus tool-result history
uses the same configured account and opaque bytes; inbound account/session
headers cannot change that selection; a bounded HTTP rejection may be classified
before commitment; a 200 SSE late error or missing terminal completes only as a
failed/incomplete committed attempt; and an ambiguous send produces one attempt,
never a second account execution.

## Device-auth user action (DEC-009)

DEC-009 adds optional `AuthResult.UserAction *AuthUserAction`, where the
provider-neutral value is `{VerificationURI string, UserCode string,
PollInterval time.Duration}`. Core projects it to transient
`AuthSession.UserAction` for the admin caller; it is not persisted. Presence is
self-describing (`nil` means no action), allowing older producers to omit it
and older consumers to ignore it. It is only an operator-presentation
projection; do not encode it into `State`, print Connector state, or let the
Connector write directly to the operator. The Connector extracts only the safe
action from the provider response and never includes a device-auth identifier,
PKCE verifier/challenge, access/refresh token, or arbitrary raw response/state.
Core validates before exposure: `VerificationURI` is 1–2048 printable ASCII
bytes without spaces/control bytes, absolute HTTPS with host and no userinfo;
`UserCode` is 1–256 printable ASCII bytes without controls; `PollInterval` is
positive. URI/code must not contain authentication secrets. The operator opens
the URI and enters the code; no
browser callback, secret-bearing URL, or agent-side browser automation is
implied.

`start` invokes Authenticate once. A supported result with `NextAction=continue`
creates the existing opaque, encrypted session with a runtime-fixed
`ExpiresAt`; the safe projection is returned for presentation. An action has a
positive provider poll interval. Each explicit
`continue --session` performs at most one poll, and a pending result returns the
next safe projection and provider poll interval. The caller waits at least that
interval before requesting another poll; no coordinator/admin infinite polling
loop is permitted. Polling never moves the fixed expiry. A result with no
continuation completes the flow and persists credentials only under the
existing acknowledged atomic credential-write rule.

`UserAction` is allowed only on `Supported=true, NextAction=continue`; it is
invalid on completed, unsupported, or refresh results. A nil action with
`continue` is a valid legacy opaque continuation needing no operator input, not
an invalid/malformed result. A Connector flow that does require user
interaction MUST return a valid action; its auth-flow conformance tests enforce
this obligation because Core cannot infer a missing presentation value from
opaque state. Presence/nil is the explicit optional-result discovery mechanism;
no new capability is introduced. If an action is malformed or inconsistent,
Core discards every result field before exposure/persistence. Start creates no
session; Continue consumes its already-claimed state/claim; an invoked Refresh
result is discarded and its marker quarantined. If consuming a Continue claim
cannot be committed, no result is exposed and DEC-007 restart recovery remains
the fail-closed backstop.

Cancellation is caller-context cancellation, not a provider action: before a
continuation call it consumes the session; after invocation begins it consumes
the claimed continuation conservatively because provider state may have been
used. The durable DEC-007 claim remains the single-winner authority; neither a
presentation value nor the caller's session handle grants claim ownership.
Expiry is checked before every continuation and cannot be extended by a
provider response. Admin output is limited to the safe URI/code, poll interval,
opaque runtime session handle, and runtime expiry; never serialize or log the
opaque state or credentials.

DEC-009 accepts this additive v1 semantic extension: existing Connectors may
omit the optional field; a Connector flow requiring operator interaction must
return it. The extension adds no operation, provider branch, persistence field,
or state-lifetime change. Older producers remain valid with a nil action and
older consumers may ignore the field. CONTRACT and M3-AUTH are synchronized;
implementations must preserve the distinct presentation/opaque-state boundary.

## OAuth credential generation and freshness (M5.1-003)

This section fixes the Codex binding over the existing account-scoped credential
row and auth coordinator under accepted
[DEC-010](../project/DECISIONS.md#dec-010-carry-credential-expiry-with-auth-results).
It uses one encrypted, versioned Connector-owned
OAuth bundle as the sole credential referenced by a Codex account. The bundle
contains the access token, optional refresh token, and trusted account identity;
the runtime treats its plaintext as opaque bytes and never parses a JWT or
provider response. The existing row's `expires_at` is the absolute access-token
expiry in UTC Unix milliseconds. The encrypted bundle and that expiry are one
credential generation: one revision CAS replaces envelope and expiry together,
and acknowledges success only after SQLite commits both. Never replace expiry
with NULL as a side effect of auth replacement. Non-Codex credential references
and their current behavior are unchanged.

`AuthResult.CredentialExpiresAt` is the optional absolute expiry metadata
accepted by DEC-010 and defined in [CONTRACT](CONTRACT.md#connector-contract)
and [M3-AUTH](M3-AUTH.md#binding-the-existing-operation). The Connector sets it
from the trusted token-exchange response; Core carries it as runtime metadata
into the atomic credential replacement and never parses provider tokens/JWTs.
For this profile the Codex Connector must return a nonzero future expiry on
every successful credential result, including refresh; this required-field rule
is enforced by Connector exchange validation and auth conformance tests. Core's
generic rule rejects any supplied zero, invalid, or non-future time and never
persists it as a live generation. Core does not need a profile/provider flag to
infer whether nil is allowed. Nil remains compatible for existing Connectors
whose credentials have no expiry. No live provider behavior is claimed.

An account with no previously authenticated access token is bootstrapped with
the existing account/credential reference and an encrypted empty bundle at a
revision, with no expiry. It is not a bearer credential: inference credential
access rejects it and readiness/configuration must not treat it as live auth.
The supported interactive start/continue flow can replace this bootstrap row
only after a successful exchange returns a complete bundle and future expiry;
the acknowledged atomic write is the only point at which login succeeds. A
missing row/reference, disabled account, unsupported auth, incomplete candidate,
or failed write is an error, not an implicit credential creation or fallback.

The Codex Connector owns a fixed **60-second refresh lead** for this profile;
it is not client- or operator-adjustable. The composition root supplies this
profile value to generic AuthCoordinator freshness policy, which has no
provider-name branch. A snapshot is fresh only when `expires_at > now + 60s`;
equality is stale. The coordinator samples time again after acquiring the
account lock and applies this same predicate before refresh and after a waiter
reloads. `AuthRequest.Action=refresh` is the existing provider-neutral selector
for the auth-scoped credential resolver: it may return this account's expired
encrypted bundle to that Authenticate call so the Connector can read refresh
material. Execute/inference continues through the ordinary resolver and rejects
expired or absent access tokens; expired material is never exposed to Execute.
No database transaction spans the Connector call.

Refresh waiters reload the account, credential revision, encrypted bundle and
expiry under the existing account lock and re-evaluate `expires_at > now + 60s`;
`Valid`/merely unexpired is insufficient to skip. If a preceding refresh
committed a newer generation still beyond the margin, the waiter returns that
generation without calling the Connector. Otherwise it may call once with that
latest revision. Cross-process CAS remains authoritative: revision conflict
discards candidates, quarantines the invoked marker as `ambiguous_result`, and
never retries the exchange or reuses candidates/possibly rotated token. Refresh markers
retain the existing M3-AUTH lifecycle; uncertain/quarantined markers block
automatic refresh and token reuse until explicit successful reauthentication.
Disabled accounts fail before invocation. Persistence failure after a possibly
successful/rotating exchange returns auth persistence failure, never exposes or
uses candidate bytes, leaves/quarantines the marker, and does not repeat the
exchange; restart recovery remains the M3-AUTH backstop.

If a successful refresh response omits `refresh_token`, the Connector retains
the prior refresh token in its replacement bundle; it must not erase it by
merging in runtime or storage. If no prior refresh token exists (including a
bootstrap generation), a response without a refresh token is rejected as
incomplete and quarantined; do not persist a short-lived bearer that cannot be
refreshed. Explicit reauthentication may establish a new complete bundle.
This is a Codex profile rule, not a Core/provider branch.

Paper trace: bootstrap has no bearer and inference fails; successful login
commits bundle + expiry + revision together. At `now + margin`, equality is
stale, so refresh can use expired access bundle material but inference cannot.
A stale waiter reloads and skips if another worker committed a fresh revision.
A missing rotated refresh token preserves the old token, while a missing token
with no old token is rejected. A stale CAS loses without overwrite/retry. If
exchange succeeds but the durable write or its acknowledgement fails, no
candidate is returned or reused and the refresh marker is quarantined; only
explicit reauthentication can resolve uncertainty.
