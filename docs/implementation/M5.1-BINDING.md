The v2 `headless` flow starts at `/api/accounts/deviceauth/usercode`, displays
the returned user code at `https://auth.openai.com/codex/device`, polls
`/api/accounts/deviceauth/token`, then exchanges returned authorization code
and verifier at `/oauth/token`. It is not RFC 8628's direct device-code token
exchange. OAuth access token becomes a Bearer token and selected account
metadata supplies `ChatGPT-Account-Id`; inbound client account/auth headers are
not selection authority. For a text paper trace, an OpenCode Responses request
containing a user `input` item and `stream:true` is sent to the profile endpoint
with that scoped bearer/account header; upstream SSE `data:` events are forwarded
as original bytes and terminal/usage information is observed separately. This
trace selects transport shape only, not authorization, successful inference or
account entitlement.

Runnable client selection is **OpenCode V2 CLI 2.0.6**, distinct from the
research source revision above. The 2.0.6 source tag is pinned in the table;
the [M1 client setup](REFERENCES.md#m1-compatibility-baseline) and retained
live evidence concern OpenAI **public API** Responses only, not ChatGPT
subscription OAuth. Thus 2.0.6 satisfies the identifiable runnable-client
selection, but its behavior against this Codex profile remains unverified. The
installed `/usr/bin/opencode` here is 2.0.21; no 2.0.6 executable was run in
this task.

## Candidate profile: `codex-responses-http-sse-v1`

| Setting | Candidate |
| --- | --- |
| Protocol | OpenAI Responses (`openai.responses.v1`); standard non-Lite dialect |
| Backend | `POST https://chatgpt.com/backend-api/codex/responses` |
| Auth | Connector-scoped `Authorization: Bearer <OAuth access token>`; selected account only in `ChatGPT-Account-Id` |
| Request/response | JSON request; `stream:true`; `Accept: text/event-stream`; preserve admitted Responses history/tool/reasoning items unless a separately reviewed translation is necessary |
| Persistence/transport | `store:false`; HTTP/SSE only; no WebSocket negotiation, Lite opt-in, remote-compaction beta or hosted tool execution |
| Candidate model | Explicitly configured identifier `gpt-5.4-mini`; presence in the Codex catalog and account availability have not been checked |
| Client | OpenCode V2 CLI `2.0.6` (runnable release, not the pinned source revision) |

The exact URL and core headers follow the pinned v2 `OpenAIPlugin.load`,
`ModelResolver.nativeCredentialSettings`, `HttpTransport.jsonRequestParts` and
Responses route, cross-checked against official Codex's HTTP client. The profile
does not assert undocumented optional originator/session headers; those require
separate compatibility evidence. Source indicates Lite-specific request
construction for certain GPT-6 catalog entries; the inspected sources do not
establish whether Lite is required for this unchecked model candidate. No
concrete mismatch was observed, so Lite remains excluded rather than silently
substituted. Candidate model availability, subscription
entitlement, device-login acceptance, endpoint behavior and live compatibility
remain unverified; later smoke gates own those claims. The `gpt-5.4-mini` choice
is a candidate configuration value, not a claim that this model appears in the
Codex catalog: public OpenAI API evidence from M1 does not establish subscription
catalog presence or entitlement.
