# M1 native Responses binding (implementation note)

This fixes the local M1 handoff against [v1](CONTRACT.md), not a new contract or a claim of live compatibility. The only admitted protocol is `openai.responses.v1` (exact match at Decode, Connector and Head); execution is native only. The sole configured target is the OpenAI public `POST /v1/responses` endpoint, model `gpt-5.4-mini`, and one explicitly selected account/credential. Decode rejects missing or different model; neither Core nor Connector rewrites the admitted body. A loopback fake target may replace the endpoint in tests, never through client routing metadata. No provider-derived account fallback or M2 target registry.

## Go handoff

- `cmd/gateway` is the composition root: load and validate startup configuration, wire one Responses HTTP Adapter, one Core and one native HTTP Connector, then register `POST /v1/responses` beside the existing probes. Initialize before readiness; shutdown stops admission, drains until the configured deadline, cancels the remainder and closes components.
- The Adapter owns HTTP Decode/Encode, bounded raw request bytes, content-type and model/feature validation, safe header selection, pre-head errors, and client writes/flushes. Accept `application/json` (optionally UTF-8 charset) with absent/identity `Content-Encoding` only; reject encoded request bodies before Execute rather than decoding/re-encoding them. HTTP chunked framing may be removed by `net/http`, but representation body bytes stay unchanged. Conceptual binding: `Decode(*http.Request) (ExecutionRequest, *GatewayError)` and `Encode(http.ResponseWriter, *http.Request, ExecutionResponse, *GatewayError) error`. Decode never selects credentials. Encode forwards Head and each Body without interpreting SSE; write failure closes the stream and cancels execution.
- Core owns trusted request/attempt IDs, one selected target/account, access/admission, requirement checks, cancellation, stream ordering and exactly-once attempt finalization. Conceptual binding: `Execute(context.Context, ExecutionRequest) (ExecutionResponse, *GatewayError)`. It does not import adapter or connector packages or parse protocol bytes. M1 uses one attempt; no automatic fallback.
- Connector owns one upstream HTTP attempt, scoped credential access and native byte forwarding, plus bounded outcome/usage observation. Conceptual binding: `Execute(context.Context, ExecutionRequest, AttemptScope) (ExecutionResponse, *GatewayError)`; `AttemptScope` is runtime-owned selection/services, never client metadata. The single-consumer stream has `Next(context.Context) (StreamFrame, error)` and idempotent `Close() error`; `Next` returns ordered Head, nonempty Body frames, Complete, then EOF. Cancellation or Close terminates the upstream request and releases its body. Core closes both discarded and delivered streams once consumption ends. Use `context`, `net/http`, `encoding/json` and bounded byte slices, not an intermediate LLM schema. These signatures are sketches; the contract's [component lifecycle and support operations](CONTRACT.md#component-descriptor-and-lifecycle) remain obligations, not optional semantics removed by this small binding.

Native Head retains the admitted protocol, safe upstream status/headers and content type. Connector makes rejection classification available at Head, even when retaining the upstream rejection body. Core decides any retry eligibility before handing Head to the Adapter; that handoff commits the attempt. Unexpected EOF/error, duplicate/out-of-order frames and client cancellation finalize once as incomplete/cancelled with partial or unknown usage; they never fabricate a successful Complete or a replacement HTTP response after commit. `Complete` is control metadata, not another body write. Use bounded reads/Body frames (at most 32 KiB each) and one bounded producer/consumer path (or synchronous pull) that blocks on a slow consumer; never queue unbounded frames, silently drop bytes/events, or buffer a complete response. When blocked on downstream writes, pause upstream reads and the stream-idle read clock; cancellation and shutdown still interrupt both sides. Idle timeout applies only while awaiting upstream progress, not while waiting for a slow client.

## Startup and eligibility

Extend the existing strict single-object JSON `-config` (1 MiB ceiling) with `upstream_endpoint` (absolute HTTPS URL ending `/v1/responses`, without userinfo/query/fragment; loopback HTTP permitted only for local tests), `upstream_credential_env` (nonempty environment variable name, not a secret), `max_request_body_bytes` (positive bounded size), `max_request_header_bytes` (positive), `connect_timeout`, `tls_handshake_timeout`, `response_header_timeout`, and `stream_idle_timeout` (positive Go durations). Keep the existing defaults for `listen` (`127.0.0.1:8080`) and `shutdown_timeout` (`5s`), 5s header-read timeout and probe behavior. If no M1 fields are supplied, retain the existing probe-only startup; when inference is configured require all new fields (no implicit upstream or limit/timeout defaults), and reject partial configuration. Validate endpoint, sizes, durations and selected credential at startup; read that env var under runtime ownership, pass only the selected credential to the Connector, and never log it. The one configured credential is the selected account scope; IDs assigned by Core are not client-selectable. Disable redirects, hidden retries and automatic gzip decompression; apply an idle timeout while reading upstream rather than a short total client timeout. Ingress over limit fails before Execute. M1 has no client virtual keys: inference and probes on the inference listener are unauthenticated **only on a numeric loopback bind** (`127.0.0.1` or `::1`); reject wildcard, hostname and other binds for inference at startup. Probe-only startup keeps its existing bind behavior. Do not use client Authorization as an upstream credential. Remote listening/auth, secret storage, multi-account selection and config reload wait for M3.

Adapter Decode derives only explicit requirements: `stream: true` needs `llm.streaming`; nonempty `tools` needs `llm.tools`; `parallel_tool_calls: true` with tools needs `llm.tools.parallel`. Recognized `reasoning`, image/audio input items and `text.format` structured output require `llm.reasoning`, `llm.vision`, `llm.audio` and `llm.structured_output` respectively. If a known feature-bearing shape cannot be identified safely, reject it rather than claim support. Unknown native fields remain opaque and byte-preserved, not automatically rejected or promoted to capabilities. Check each required identifier against both Adapter and Connector for this protocol/native mode/selected model/account: only `supported` on both sides admits execution, absent/`unknown`/`unsupported` rejects as `unsupported_feature`. This fixed check is not an M2 registry.

Separate **declaration** from **verification**: an M1 scoped `supported` declaration for the selected account/model may be enabled only for features established by both a local Adapter/Connector fixture and observed direct-provider behavior for that same account/model (then tested through the gateway); mere model selection or FND-005 source review does not establish support. Bootstrap the [M1 smoke gate](ROADMAP.md#m1--transparent-responses-proxy) with its direct-client leg first; if access or actual parallel tool calls cannot be demonstrated, leave those requirements `unknown`, reject them at the gateway, and record the smoke criterion as unverified rather than bypassing eligibility. Fixture-only declarations are for the fake upstream, not the live account. Support is scoped and may change; execution failure remains possible even after admission. No claims for untested reasoning or exact usage.

## Connector observation without response buffering

Forward native response bytes as read (and flush at the Adapter), while a Connector-only side observer inspects bounded metadata for classification. For fixed JSON, inspect up to 1 MiB for `error`, `status` (`failed`, `incomplete`, `completed`) and usage; above that limit keep forwarding but finish incomplete/usage unknown unless a bounded incremental observer can prove the terminal outcome. For SSE, parse incremental UTF-8-safe event lines across read boundaries and multiline `data`, including events larger than 256 KiB. Stream-scan JSON tokens for terminal event name/type, status/error and usage with at most 4 KiB of retained field/scalar scratch; skip arbitrarily large irrelevant strings/fields without retaining an event or requiring its bytes at once. A large terminal `response.completed` containing output items must still be observable; if required terminal metadata is malformed or exceeds the bounded scalar budget, finish incomplete rather than infer success. Recognize `response.completed`, `response.failed`, `response.incomplete` and `error`. No unbounded event queue: observe inline under downstream backpressure. Preserve opaque bytes, including unknown fields and original line endings. HTTP rejection is failed regardless of a JSON/SSE body. A recognized HTTP-200 failure event/object is failed with classified cause, not success from HTTP status. Success requires a recognized terminal completed state; truncated JSON, EOF without terminal SSE, unobservable terminal metadata or malformed/unrecognized terminal content ends incomplete with classified cause. Extract known usage from terminal data when valid; missing or ambiguous usage is unknown, not zero. Never expose raw provider diagnostics as a client-safe GatewayError.

Send `Accept-Encoding: identity`, disable transport gzip decoding, and do not decompress/recompress. If upstream supplies non-identity `Content-Encoding` anyway, including on an HTTP rejection, return a classified pre-Head error and close upstream: encoded JSON/SSE cannot be safely observed under this binding, so that encoded rejection body is **not** forwarded. Preserve the known rejection status only as sanitized error metadata; do not claim safe replay solely from this rejection because the upstream request may already have executed. Native forwarding preserves length headers only when consistent with unchanged bytes, filtering hop-by-hop and credential headers. M2 may add evidence-backed connector capabilities; M3 owns remote auth/storage/accounting persistence; translation, sessions, async, IPC and automatic fallback are outside M1.
