# M2-016 — Dispatch through registry, route and scoped context

## Outcome

Core executes the selected common Connector through one provider-agnostic attempt path. See [registry](../TASKS.md#m2--connector-api-and-conformance-baseline) and [M2](../ROADMAP.md#m2--connector-api-and-conformance-baseline).

## Scope

- Wire `Dispatcher` execution to use `RouteTable` selection, admitted `Registry` components, scoped eligibility validation (`EligibilityCandidate.Eligible`), and `InvocationServices` for attempt credentials and transport.
- Enforce runtime-owned request identity and attempt scope (`ID`, `AccountID`, `Mode`); client metadata or extension headers cannot override trusted route identity or credentials.
- Execute via the common `core.Connector.Execute(ctx, in, scope, services)` interface without provider-specific branches or concrete connector imports in Core.
- Preserve checked stream, cancellation, pre-Head failure handling, and once-only terminal `Finalize` callback. Keep exactly one attempt; errors retain retry metadata without triggering replay or fallback.
- Retain backward compatibility for the legacy `Target` dispatch path when `Routes` is not configured, keeping M1 gateway tests green until M2-019/M2-020 composition.

## Acceptance

- [x] Client IDs/metadata cannot override trusted selection or credentials; unknown requirements fail before execution.
- [x] Two distinct Connector implementations execute through common dispatch without provider-name branches; ineligible requests make zero Execute/service calls.
- [x] Pre-Head failure and unexpected-stream cleanup remain covered by the shared attempt-stream tests; dispatch calls one attempt and never retries.
