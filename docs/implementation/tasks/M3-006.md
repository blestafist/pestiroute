# M3-006 — Create account and credential schema

## Outcome

Add versioned migration 2 to the SQLite storage migration engine establishing the `accounts` and `credentials` relational schema, integrity constraints, and indexes. This is one bounded deliverable in the [M3 registry](../TASKS.md#m3--access-accounts-and-accounting) toward [M3](../ROADMAP.md#m3--access-accounts-and-accounting).

## Scope

- Add version 2 to `schemaMigrations` in `internal/storage/sqlite/migrate.go` creating:
  - `accounts` table: `id TEXT PRIMARY KEY`, `connector TEXT NOT NULL`, `enabled INTEGER NOT NULL DEFAULT 1 CHECK (enabled IN (0, 1))`, `created_at INTEGER NOT NULL`, `updated_at INTEGER NOT NULL`.
  - `credentials` table: `id TEXT PRIMARY KEY`, `account_id TEXT NOT NULL REFERENCES accounts(id) ON DELETE RESTRICT`, `format_version INTEGER NOT NULL`, `key_version TEXT NOT NULL`, `nonce BLOB NOT NULL`, `ciphertext BLOB NOT NULL`, `expires_at INTEGER`, `revision INTEGER NOT NULL CHECK (revision >= 1)`, `created_at INTEGER NOT NULL`, `updated_at INTEGER NOT NULL`, with `UNIQUE (account_id, id)`.
  - Index `idx_credentials_account_id ON credentials(account_id)`.
- Use UTC Unix-millisecond integers (`INTEGER`) for entity created, updated, and expiry timestamps per M3-STORAGE.md; operational migration journal `schema_migrations.applied_at` retains RFC3339 text established by M3-005.
- Ensure schema compatibility with the existing migration runner, preserving WAL, `synchronous=FULL`, foreign keys, and 500 ms busy timeout.
- Explicit limits: no AES-GCM encryption/decryption logic or master-key loading (belongs to M3-009); no credential repository persistence or CAS operations (belongs to M3-010); no account repository lifecycle methods (belongs to M3-011); no auth sessions (belongs to M3-034); no virtual key, request, or attempt tables (belong to M3-007 and M3-008).

## Acceptance

- [x] Version 2 migration applies atomically via `Migrate` on top of version 1 or fresh database, recording version 2 in `schema_migrations`.
- [x] Duplicate IDs in `accounts` or `credentials` are rejected by primary key constraints.
- [x] Foreign key constraints enforce referential integrity: inserting a credential with a nonexistent `account_id` fails, and deleting an account referenced by credentials fails under `ON DELETE RESTRICT`.
- [x] Updating an account's `enabled` state to 0 (disabled) does not delete or invalidate existing credential records or historical references.
- [x] Revision checks reject non-positive revisions (`revision < 1`), and `UNIQUE (account_id, id)` is enforced.
- [x] Account/credential timestamps use `INTEGER` UTC Unix milliseconds; `schema_migrations.applied_at` retains its version-1 RFC3339 text format.
- [x] No plaintext secret or master key columns exist in schema table definitions.
- [x] `PRAGMA foreign_key_check` passes with zero violations across sample accounts and credentials.
- [x] Failed migration statement in a test migration rolls back atomically, leaving the database at version 1 without partial DDL.
- [x] Existing migration idempotency and future-schema refusal tests continue to pass with the new migration version.
