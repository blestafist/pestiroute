## Scope

- Create standalone automated recovery test script `scripts/verify-recovery.sh` testing:
  1. Creation of protected SQLite state (account, encrypted credential, policy, key, and live fake-upstream request writing usage records).
  2. Online consistent backup using SQLite backup API (`sqlite3 "$DB" ".backup '$BACKUP'"`), proving no raw file copying of an active WAL database as a standalone backup.
  3. Offline restore to a separate database path (`$RESTORED`), verifying `PRAGMA integrity_check` returns `ok` and `PRAGMA foreign_key_check` returns empty.
  4. Validation that the restored database preserves accounts, policies, virtual keys, and usage records, and decrypts the encrypted connector credential with the original external master key.
  5. Validation that absent or malformed external master key files fail closed at startup and admin command execution, and a valid wrong 32-byte key fails closed on credential use with zero upstream delivery and no secret disclosure.
  6. Startup and serving of a protected request to a deterministic fake upstream against the restored database using the restored virtual key.
  7. Verification of an actual schema-v5 database served by a compatible historical gateway before backup to create usage history, untouched v5 pre-upgrade backup, stopped v5→v6 migration with persisted data checks, rejection of the actual v6 DB by the v5 binary, and rollback by restoring the v5 backup to a fresh path where the v5 gateway passes readiness and serves an authenticated credential-backed request with preserved history.
  8. Safe restore promotion: restore only to a fresh path using a validated staging file; failed/corrupt or repeated restore must not replace or partially corrupt an existing database, and a corrupt source must not leave a destination behind.
  9. Preserve a revoked virtual-key fixture and prove the restored key remains denied without upstream delivery.
- Update `deploy/README.md` with explicit operator runbook sections for consistent backup, offline restore to a distinct path, integrity checks, missing/wrong-key handling, stopped migration, and disaster recovery rollback.
- Limits: Single-node Linux/amd64 only; no remote databases, network shares, replication, or background backup services. No automatic in-place downgrade or master key rotation (not implemented). No changes to core contracts, schema migrations, or CLI flags.
