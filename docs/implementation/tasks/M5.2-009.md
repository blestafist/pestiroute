# M5.2-009 — Implement evidence-scoped model and capability declarations

## Outcome

Implement evidence-scoped model and capability declarations for the local-runtime Connector in `internal/connector/responses`. Ensure configured local model IDs query and route only within exact matching scopes (`protocol == "responses"`, `mode == "native"`, configured model ID, and configured account ID); reject duplicate JSON keys or invalid capability declarations at startup; prevent unevidenced `core.Supported` declarations on model-dependent capabilities without reviewed runtime version/model/profile evidence; and prevent loopback endpoints from implicitly upgrading local model capabilities. One bounded result in [the M5.2 registry](../TASKS.md#m52--local-runtime-connectors), under [ROADMAP M5.2](../ROADMAP.md#m52--local-runtime-connectors).

## Scope

- In `internal/connector/responses`:
  - Enhance `Connector.Init`, `Capabilities`, `capabilitiesLocked`, and `Models` for local-runtime connectors (`c.local == true`):
    - Configured local model ID is reported through `Models` and matched by `Capabilities` only when the query scope matches exactly: `Protocol == "responses"`, `Mode == "native"`, `Model == c.model`, and `AccountID == c.accountID`. Mismatches return empty capability results and empty Models results.
    - JSON decoding / validation in `Init` must detect and reject duplicate JSON object keys (including duplicate capability entries) rather than silently allowing last-key-wins overwrites.
    - Capability evidence gating: model-dependent capabilities (`llm.tools`, `llm.reasoning`, `llm.tools.parallel`) cannot be declared `core.Supported` without reviewed runtime version/model/profile evidence (which remains unverified in this offline stage per M5.2-007). Any configuration declaring `Supported` for model-dependent capabilities without reviewed profile evidence fails `Init`. Missing/unreviewed capabilities evaluate to `core.Unknown`.
    - Local connectors never inherit native `gpt-5.4-mini` capability defaults, and loopback / fixture endpoints (`fixtureEndpoint`) cannot implicitly upgrade local model capabilities to `core.Supported`.
    - Parallel tool calling (`llm.tools.parallel`) remains `Unknown` absent reviewed evidence.
    - Usage estimation (`EstimateUsage`) remains unsupported (`Supported: false, Known: false`).
  - Unit and race tests in `internal/connector/responses/component_test.go`:
    - Prove arbitrary local model ID routes and queries under exact matching scope.
    - Prove scope mismatches (protocol, mode, model, account) return empty results.
    - Prove `Init` rejects duplicate JSON keys, duplicate capability declarations, empty model/account, and invalid capability states.
    - Prove `Init` rejects unevidenced `core.Supported` declarations on model-dependent capabilities.
    - Prove loopback local endpoints do not elevate undeclared capabilities to `core.Supported`.
    - Prove native connector (`pestiroute.responses.native`) behavior and fixture upgrades remain completely backward compatible.
- Explicit limits:
  - No gateway YAML route composition changes in `cmd/gateway/yaml_config.go` (deferred to M5.2-013).
  - No preflight request body validation for unsupported semantics (deferred to M5.2-012).
  - No synthetic wire fixture additions (deferred to M5.2-010).
  - No real backend calls, live runtime installation, or container execution.
