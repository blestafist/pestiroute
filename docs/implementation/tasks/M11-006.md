# M11-006 — Bridge the existing auth coordinator to admin HTTP

## Outcome

Expose generic authentication lifecycle endpoints on the authenticated admin HTTP API by bridging to the existing `core.AuthCoordinator`, matching the administrative OpenAPI specification and store/CLI semantics. Registered in [TASKS](../TASKS.md#m11-administrative-http-api) and scoped in [M11](../M11-ADMIN-API.md).

## Scope

- Implement auth lifecycle handlers in `internal/admin`:
  - `POST /admin/v1/auth/sessions`: accepts strict JSON body `AuthStart` (`{"account_id": "string"}`). Starts an auth session via the coordinator for the specified account. Returns 200 `AuthResult` (`{"status": "complete"|"continue", "session_id": "...", "expires_at": "...", "user_action": {"verification_uri": "...", "user_code": "...", "poll_interval_seconds": ...}}`).
  - `POST /admin/v1/auth/sessions/{session_id}/continue`: accepts strict JSON body `AuthContinue` (`{"callback_input": "string"}`). Max length 4096 characters (`writeOnly`). Advances session via coordinator `Continue(ctx, sessionID, callbackInput)`. Returns 200 `AuthResult`, or 409 `revision_conflict` (or appropriate error) on stale/replayed/mismatched session.
  - `POST /admin/v1/auth/accounts/{account_id}/refresh`: invokes coordinator `Refresh(ctx, accountID)`. Returns 200 `AuthRefresh` (`{"status": "refreshed", "revision": <int64>}`). Returns 404 on unknown account, 400 on disabled account, or 409/503 on quarantined/unavailable refresh.
- Wire coordinator access into `internal/admin.Config` / `internal/admin.New`:
  - Provide an `AuthCoordinator` interface or coordinator adapter in `internal/admin` allowing invocation of start, continue, and refresh.
  - Wire coordinator in `cmd/gateway/main.go` for the admin listener when runtime DB, master key, and accounts are configured.
- Explicit limits:
  - Do not invent quota tasks, live quota scraping, or billing estimates.
  - No provider-specific HTTP routes or query parameters; generic start/continue/refresh only.
  - Callback input is transient: max 4096 bytes/characters, writeOnly, never persisted or logged in plain text.
  - Never decrypt or return tokens/secrets in responses; credentials and internal tokens remain hidden.
  - Safe `UserAction` projection only (verification_uri, user_code, poll_interval_seconds).
  - Stale, replayed, expired, disabled-account, or revision-conflicting continuations fail closed (404/409).
  - Default Claude provider gate retained (DEC-020). Claude production routing remains disabled / gated.
  - No background polling loop or automatic retry in the HTTP layer; single invocation of coordinator.
  - UI / read endpoints (`GET /admin/v1/...`) must never trigger auth refresh or mutate auth state.

## Acceptance

- [x] `POST /admin/v1/auth/sessions` accepts valid `account_id`, starts a coordinator session, and returns 200 `AuthResult` with opaque `session_id`, expiry, and sanitized `user_action` (verification URI, user code, polling interval); non-existent or disabled accounts return appropriate error (404/400).
- [x] `POST /admin/v1/auth/sessions/{session_id}/continue` advances auth session with bounded `callback_input` (<= 4096 chars) and returns updated 200 `AuthResult` (status continue or complete).
- [x] Stale, replayed, expired, or wrong-account sessions return 409 conflict or 404 not found; one-time claim semantics enforced.
- [x] `POST /admin/v1/auth/accounts/{account_id}/refresh` invokes single refresh, persists updated revision, and returns 200 `AuthRefresh` with new revision number; never reveals credential secrets.
- [x] Quarantined, disabled, or missing accounts reject refresh requests; Claude default-disabled gate is retained without live bypass.
- [x] No GET or read endpoint triggers auth coordinator refresh or state mutation; callback input and credentials are never reflected in error envelopes, logs, or responses.
- [x] Oversized bodies (> 4096 callback input), unknown JSON properties, and missing bearer auth return 400, 413, or 401.
