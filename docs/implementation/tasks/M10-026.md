# M10-026 — Support standard-tier onboarding candidate and exhaustive eligibility diagnostics

## Outcome

Support explicit known `standard-tier` as an eligible managed onboarding candidate alongside `free-tier` when uniquely advertised as default (`isDefault: true`), evaluate all terms, privacy, user-project, and ineligibility guards exhaustively for diagnostic clarity before returning errors, and send the selected candidate `tierId` in the single onboarding POST with `cloudaicompanionProject` omitted. See [TASKS.md](../TASKS.md#m10--google-antigravity-connector) and [M10 brief](../M10-ANTIGRAVITY.md).

## Scope

- Owning ADR DEC-025 and Specification Synchronization:
  - Amend [DEC-025](../../project/DECISIONS.md#dec-025--bound-experimental-antigravity-managed-project-onboarding) and [M10-AUTH-BINDING](../M10-AUTH-BINDING.md#missing-project-onboarding-audit-m10-022) to recognize explicit known `standard-tier` as eligible for managed onboarding when uniquely advertised as default.
  - Document that `standard-tier` name alone does not indicate paid resource billing or zero charge; operator explicit authorization bounds onboarding to existing account entitlements within the <=1000 request experiment without billing, payment, API enablement, or resource creation endpoints.
- Connector Implementation in `internal/connector/antigravity/auth_onboard.go`:
  - Broaden candidate predicate (`eligibleFreeTier` / `eligibleOnboardingTier`) to admit both `free-tier` and `standard-tier`:
    - Candidate match: `id == "free-tier" || id == "standard-tier"`.
    - Default requirement: candidate must have `isDefault == true`. Never select `legacy-tier` or unadvertised/arbitrary fallback tiers.
    - Candidate count: exactly one candidate with `isDefault == true` must exist; 0 yields `candidate_missing`, >1 yields `ambiguous`.
    - User project requirement: `userDefinedCloudaicompanionProject` must be absent, null, or boolean `false`; `true` fails closed with `userprojectrequired`.
    - Terms acceptance: `hasAcceptedTos` absent or boolean `true` is allowed; explicit `false` fails closed with `terms` (invalid type fails with `schema_invalid`).
    - Privacy notice: `privacyNotice.showNotice` must be absent, null, or boolean `false`; `true` fails closed with `privacy`; any other type is `schema_invalid`.
    - Provider ineligibility: candidate must not be listed in `ineligibleTiers`; if listed with reason `VALIDATION_REQUIRED` yields `validationrequired`, otherwise `providerineligible`.
    - Candidate ambiguity: multiple default tiers or duplicate candidate entries fail closed with `ambiguous`.
    - Existing guards preserved: `currentTier` present fails closed (`auth_project_missing`); `paidTier` present fails closed (`paid_present`).
  - Diagnostic classification in `tierEligibilityDiagnostic`:
    - Check terms, privacy, user project, and provider ineligibility for discovered candidate tiers before returning diagnostics, ensuring actionable metadata flags (`default`, `userproject`, `terms`, `ineligible`) are emitted rather than premature `candidate_missing` when a default standard-tier is present.
    - Emit fixed safe tier classes (`free`, `standard`, `legacy`, `other`) without raw IDs or provider response bodies.
  - Dynamic Onboarding POST in `onboardProject`:
    - Format single POST payload with the selected candidate's `tierId` (`"standard-tier"` or `"free-tier"`): `{"tierId":"...","metadata":{"ideType":"IDE_UNSPECIFIED","platform":"PLATFORM_UNSPECIFIED","pluginType":"GEMINI"}}`, omitting `cloudaicompanionProject`.
    - Preserve same-origin GET LRO polling (max 12 polls, 2s interval, 30s deadline) and durable request budget accounting (atomic reservation, ceiling <=1000, never reset).
- Safeguards and Limits:
  - No additional HTTP requests for diagnostics or logging.
  - No reading existing fixture files, database keys, client secrets, callback data, or logs.
  - 0 live/provider network calls; offline unit, integration, and CLI tests only.
- Conformance & Regression Tests:
  - Truth table conformance in `internal/connector/antigravity/auth_onboard_test.go` and `cmd/gateway/admin_auth_test.go`:
    1. Standard-tier happy path: immediate done and polled LRO.
    2. Standard-tier negative cases: `terms` false, `terms` malformed type, `userprojectrequired` true, `providerineligible`, `validationrequired`, `ambiguous` (multiple defaults / duplicates), schema invalid.
    3. Regression tests for existing `free-tier` happy path and negative cases.
    4. Canary assertions proving zero token, secret, raw payload, or unclassified tier ID leakage.
