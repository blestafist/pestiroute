# M3-039 — Execute bounded fallback with durable attempt accounting

## Outcome

Execute bounded fallback with durable attempt accounting across authorized route candidates before stream commitment. This is one bounded deliverable in the [M3 registry](../TASKS.md#m3--access-accounts-and-accounting) toward [M3](../ROADMAP.md#m3--access-accounts-and-accounting).

## Scope

- Integrate ordered candidate fallback into `Dispatcher.Execute` using candidate order from `AuthorizedCandidates` and retry decisions from `DecideRetry`.
- Handle safe uncommitted attempt failures (pre-Head error or rejected Head); close and finalize the initial attempt before evaluating, admitting, and executing the next candidate.
- Preserve single RequestID and single RPM reservation across all attempts; generate a distinct AttemptID and reserve/reconcile TPM for each executed attempt.
- Re-verify policy authorization, route limits, capability match, and token budget for each fallback candidate before invocation.
- Halt retry immediately on stream commitment, context cancellation, deadline expiry, non-retryable disposition, or accounting storage failure (failing closed).
- Pure in-process fallback execution; no cross-target response stitching, no protocol translation, and no multi-credential balancing.

## Acceptance

- [x] A safe uncommitted attempt failure (pre-Head error or rejected Head) advances to the next authorized candidate when permitted by `DecideRetry`.
- [x] Response commitment (stream frame delivered), context cancellation, deadline expiry, or accounting storage failure prevents any subsequent attempt.
- [x] Each started attempt receives a distinct AttemptID, is finalized once with terminal status, and reconciles its token reservation; the request-level RPM admission remains singular.
- [x] Fallback candidate enforces route limits, capabilities, policy authorization, and token budget admission; exhausted candidates or failed budget returns the client-safe terminal failure without retrying.

## Completion Evidence

Implemented bounded fallback in `internal/core.Dispatcher`. One runtime RequestID is shared across attempts; each invocation creates a distinct AttemptID. The first candidate uses `AccountingStore.Admit` once, while alternatives are re-authorized and re-estimated before `AccountingStore.BeginAttempt` reserves TPM without another RPM admission. Every dispatched attempt is gated by its own durable dispatch intent and finalized once before the next candidate is considered. Only explicit safe retry metadata before commit can advance; rejected Head is finalized before handoff, and a successful Head is prefetched without buffering the response stream. When configured, the overall deadline starts immediately before initial durable request admission and remains active through all attempts and stream completion; it is never reset on fallback. Parent cancellation remains active throughout. Attempt bounds, cancellable RetryAfter, candidate exhaustion, cancellation, budget rejection, and accounting failure stop replay. Pre-Head settlement failures are surfaced before retry; storage degradation is shared with the parent Dispatcher.

Protected YAML `retry.max_attempts` and `retry.deadline` flow through startup normalization, `topologyRoute`, and dispatcher construction; omitted retry configuration remains one attempt. The planner's accepted [M3-CONFIG](../M3-CONFIG.md#retry-mapping-and-candidate-limits) deadline semantics govern: the single deadline starts immediately before initial admission, covers the complete request and all attempts, and is not extended on retry. Route group order, candidate authorization/limits/capabilities, payload bytes, and per-candidate account scope are preserved.
