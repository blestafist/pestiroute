# M3-036 — Exercise authentication through CLI with a scripted Connector

## Outcome

Exercise authentication through CLI with a scripted Connector. Provide an administrative CLI command path (`gateway admin auth <start|continue|refresh>`) that delegates interactive session management and token refresh to the runtime `AuthCoordinator`, presenting clear next-action guidance and unforgeable session handles while strictly redacting secrets from standard streams and process logs. This is one bounded deliverable in the [M3 registry](../TASKS.md#m3--access-accounts-and-accounting) toward [M3](../ROADMAP.md#m3--access-accounts-and-accounting).

## Scope

- Add the `gateway admin auth <start|continue|refresh>` CLI subcommand path in `cmd/gateway/admin_auth.go` (dispatched from `cmd/gateway/admin.go`):
  - `start --account <ID>`: initiates interactive flow via `AuthCoordinator.Start`; outputs session handle and expiry if continuation is required, or completion status; reports unsupported honestly if connector rejects auth.
  - `continue --session <ID>`: resumes interactive flow via `AuthCoordinator.Continue`; outputs next continuation handle or completion status; fails closed on expired, consumed, or invalid sessions.
  - `refresh --account <ID>`: executes serialized token refresh via `AuthCoordinator.Refresh`; outputs updated revision status on success; returns classified error without false success on persistence failure.
- Enforce global admin flags (`--db`, `--master-key`), master-key validation, schema currency, and stream injection (`stdin`, `stdout`, `stderr`).
- Connect runtime coordinator to admin environment:
  - Wire `sqliteAuthCoordinatorStore` with database and loaded master key.
  - Support registry injection or connector construction for admin execution, allowing test harnesses to supply scripted connectors while production defaults to configured/registered connectors.
- Acceptance and safety testing in `cmd/gateway/admin_auth_test.go`:
  - Test-injected scripted connector exercising multi-step `start` -> `continue` -> completion and serialized `refresh`.
  - Process restart survival: execute `start` in one injected CLI invocation, then `continue` in a distinct CLI invocation against the same database.
  - Built-in native connector (`responses` connector) test: verify it honestly reports unsupported OAuth without claiming success or generating dangling sessions.
  - Redaction & safety: assert session state ciphertexts, tokens, and master keys never appear in stdout, stderr, or error strings.
  - Post-exchange persistence failure: assert injected storage failure after connector exchange produces a distinct classified error (`authentication persistence failed`) rather than success.
- Explicit limits:
  - Real provider OAuth/browser handling and network callbacks belong to M5.1.
  - No new public/remote HTTP admin endpoints or daemon listeners.
  - Core runtime (`internal/core`) remains unchanged.

The command syntax is:

```bash
gateway admin --db ./state/gateway.db --master-key ./state/master.key auth start --account ACCOUNT_ID
gateway admin --db ./state/gateway.db --master-key ./state/master.key auth continue --session SESSION_HANDLE
gateway admin --db ./state/gateway.db --master-key ./state/master.key auth refresh --account ACCOUNT_ID
```

`start` prints an opaque runtime-generated session handle and fixed expiry only when continuation is needed; pass that handle directly to `continue`. Connector state, credentials, and master-key bytes are never CLI arguments. Tests inject the scripted/native connector registry into isolated `runAdmin` invocations; the executable does not expose a remote admin API or fabricate provider OAuth support.
