Implement an offline OAuth PKCE state machine and token refresh flow for Claude Code in `internal/connector/claudecode` under DEC-018 once the contract path for interactive browser authentication is resolved. ## Scope

- Implement offline state machine in `internal/connector/claudecode`:
  - `start`: generate PKCE verifier/challenge (S256), state parameter, and authorization URL.
  - `continue`: exchange authorization code for access/refresh token bundle against synthetic endpoint.
  - `refresh`: atomic token refresh using stored refresh token without replaying ambiguous exchanges.
- Explicit limits: Offline synthetic implementation only. No live calls, no real credential storage, no browser automation.

## Acceptance

- [ ] Generates valid PKCE S256 challenge and verifier in initial start step.
- [ ] Opaque continuation state strictly protects verifier and session state without exposing secrets.
- [ ] Expiry and tokens parsed accurately from synthetic response fixtures.
- [ ] Safe non-replaying token refresh state transitions.

## Open Questions / Blocker

BLOCKED pending ADR and contract update:
1. Under v1 CONTRACT and [DEC-009](../../project/DECISIONS.md#dec-009--separate-safe-user-actions-from-opaque-auth-state), `AuthUserAction` requires both `VerificationURI` and a non-empty `UserCode`. The observed Claude Code flow is standard browser OAuth without a user/device code; injecting dummy codes or state into `UserCode` violates the contract.
2. Under [M3-AUTH](../M3-AUTH.md#binding-the-existing-operation), `AuthRequest` receives only host-managed continuation state; there is no client/redirect callback input field for returning the authorization `code` and `state`.
3. Unblock condition: An approved ADR amending `core.AuthUserAction` and `core.AuthRequest` or establishing an explicit callback bridge contract, without silent semantic alterations.
