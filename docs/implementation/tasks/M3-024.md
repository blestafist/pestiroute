## Scope

- In `internal/storage/sqlite`, implement atomic admission and attempt reservation operations on `Ledger` (matching `AccountingStore` admission operations and schema v4 `requests`, `attempts`, `reservations` tables):
  - Initial admission (`Admit`): execute in a single `BEGIN IMMEDIATE` write transaction. Check virtual key RPM against rolling 60s window (`accepted_at > now - 60000 && accepted_at <= now`), and TPM against held reservations (all `held` reservations for the key) plus settled charges within rolling 60s window (`reconciled_at > now - 60000 && reconciled_at <= now`) plus candidate estimate. If within limits, insert request row (`state='admitted'`), attempt row (`state='reserved'`), and reservation row (`state='held'`).
  - Subsequent attempt admission (`BeginAttempt`): execute in a single `BEGIN IMMEDIATE` write transaction. Verify existing admitted request, check attempt TPM budget without charging RPM again (`AdmissionUnits(false, estimate)`), and insert attempt row (`state='reserved'`) with incremented ordinal and reservation row (`state='held'`).
  - Strict rollback: any limit exhaustion, foreign key failure, or storage error rolls back completely without writing partial request, attempt, or reservation records.
  - Idempotency: duplicate request or attempt admission with identical parameters is idempotent; conflicts or invalid states return `ErrLedgerConflict`.
  - Non-positive reservations, negative limits, or overflow fail closed; zero is never a valid reservation. No network or Connector calls occur within the transaction.
- Explicit limits:
  - Does not mark dispatch intent (reserved for [M3-025](M3-025.md)).
  - Does not reconcile terminal usage or release reservations (reserved for [M3-026](M3-026.md)).
  - Does not wire admission into Core dispatch or HTTP handlers (reserved for [M3-027](M3-027.md)).
  - Does not implement startup recovery of interrupted attempts (reserved for [M3-029](M3-029.md)).
