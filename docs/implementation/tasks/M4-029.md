## Scope

- Field-by-field protocol representability analysis between OpenAI Responses reasoning and Anthropic Messages extended thinking for OpenCode 2.0.6 and `claude-opus-5-5`:
  - Request controls: client `reasoning.effort` and `reasoning.summary` vs provider `thinking.type: "enabled"`, `thinking.budget_tokens`, and Anthropic's requirement of `temperature: 1` (or omitted).
  - Stream items: Responses `response.output_item.added` (`type: "reasoning"`, `summary`, `encrypted_content`) vs Messages `thinking` blocks (`thinking`, `signature`) and `redacted_thinking` (`data`).
  - Conversation history replay: Anthropic requirement that thinking blocks with valid signatures precede `tool_use` blocks in assistant history turns vs Responses replaying reasoning items.
- Formulate and record the normative decision in `docs/implementation/M4-BINDING.md` (or an ADR in `docs/project/DECISIONS.md` if an extension is warranted):
  - Evaluate whether reversible representation is achievable without violating architectural guardrails (no false ciphertext claims, no plain-text flattening into assistant `output_text`, no hidden state in the gateway, no Core reasoning parsing).
  - If reversible lossless replay cannot be achieved without falsifying ciphertext or losing required signatures, formally declare reasoning unsupported/unknown for this translation profile, requiring local fail-closed rejection of reasoning inputs/blocks.
- Implement deterministic probe tests in `internal/connector/anthropic/` verifying the representability boundary or fail-closed rejection of unsupported reasoning controls and history items.
- Explicit limits: Do not implement full reasoning streaming or tool-round execution (owned by M4-030 and M4-031). Do not modify Core routing or add provider-specific branching in Core.
