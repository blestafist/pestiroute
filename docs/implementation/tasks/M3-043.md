## Scope

- In `cmd/gateway` (e.g. `cmd/gateway/durable_cancellation_test.go`):
  - Add end-to-end cancellation, stream violation, and storage failure tests combining `core.Dispatcher`, `sqliteAccountingStore`, and file-backed SQLite:
    - Pre-Head client cancellation: client context is canceled before first stream frame; upstream observes local teardown, no downstream frame is written, attempt is finalized as `cancelled` or `failed`, and reservation is released (0 net charge) or conservative if dispatch intent was committed.
    - Post-Head client cancellation and caller `Close()`: client cancels context or caller closes stream mid-generation; upstream observes teardown, blocked Next unblocks and releases, attempt is finalized with terminal status `cancelled` or `interrupted`, conservative TPM reservation is settled, and usage counts remain NULL (unknown).
    - Blocked producer and bounded backpressure under slow/failing storage: verify bounded queue buffers and teardown unblocking; storage contention or terminal persistence failure does not deadlock or exceed memory bounds.
    - Upstream protocol and stream violations: connector emits malformed stream sequence (e.g., missing Head, data after Complete/EOF, invalid framing); Dispatcher rejects stream, closes producer resources, prevents fallback after commit, and finalizes attempt as `failed` with exact failure category.
    - Downstream encode/write failure: stream disconnect during response encoding terminates stream, releases resources, and terminally settles accounting without duplicate refunds or panics.
- Explicit limits:
  - Pure verification test suite; no changes to Core contracts, stream framing, schema migrations, or public CLI interfaces.
  - Deterministic loopback fake upstream and scripted connectors; no real provider credentials or paid inference.

## Acceptance

- [x] Each started attempt has one terminal/recoverable identity in SQLite; no duplicate usage records or double reservation refunds occur under stream cancellation, caller Close(), or storage contention races.
- [x] Pre-Head cancellation releases reservations cleanly (zero charge if undispatched); post-Head cancellation or interruption terminally settles conservative token reservations with NULL/unknown usage.
- [x] Incremental delivery and bounded backpressure remain intact under slow or contended storage; no unbounded buffering or goroutine leaks occur.
- [x] Committed stream failures or downstream write errors terminate according to Adapter/Connector semantics, with no replacement HTTP response or fallback candidate execution; upstream producer resources close cleanly.
