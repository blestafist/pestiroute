# M1-017 — Bounded slow-consumer backpressure

## Outcome

A stalled client cannot make application queues or response buffers grow with total stream size. See [registry](../TASKS.md#m1--transparent-responses-proxy-planning-candidates) and [M1](../ROADMAP.md#m1--transparent-responses-proxy).

## Read First

- `internal/connector/responses/sse.go`, `internal/adapter/responses/encode.go`, `cmd/gateway/main_test.go`
- [Backpressure contract](../CONTRACT.md#execution-response-and-streamframe)
- [Testing levels](../TESTING.md#testing-levels)

## Scope

- In `internal/connector/responses/sse.go`, `internal/adapter/responses/encode.go`, and integration in `cmd/gateway`, verify that read-ahead across Connector, Core, and Adapter is bounded (synchronous chunk consumption with 4096-byte read buffer and <=4 KiB scalar observer scratch; no background goroutine buffering).
- Add integration coverage in `cmd/gateway/main_test.go` (and unit tests if needed in `internal/connector/responses/sse_test.go`) simulating a stalled downstream consumer with a large multi-chunk SSE stream.
- Verify:
  1. Stalled downstream consumer blocks upstream write/read progression once network buffers saturate;
  2. Resuming downstream consumption completes and preserves exact stream bytes;
  3. Client cancellation while stalled releases upstream request and resources promptly.
- Stop before production QoS policies, load testing, or treating stalls as implicit disconnects (idle timeouts belong to M1-018).

## Acceptance

- [x] Application buffer/queue capacities are bounded and independent of total response length (<=4 KiB chunk size, <=4 KiB observer scratch; zero unbounded channel/buffer queues).
- [x] Controlled upstream producer stalls when downstream reader stops reading; downstream resuming consumes all stream bytes without truncation or memory growth.
- [x] Client context cancellation while stalled under backpressure promptly cancels upstream request and closes connections without leaking goroutines.

## Open Questions / Blocker

None. The streaming pipeline is synchronously driven by downstream `Next()` / `Write()` calls with bounded 4 KiB buffers; existing `fakeupstream` steps and TCP client pipes provide direct backpressure control without external dependencies.

## Completion Evidence

Implemented a 4 KiB SSE read buffer; Adapter remains synchronous `Next`/`Write`/flush with no queues. `TestSSEReadChunkHardBound` directly feeds 64 KiB plus a terminal event and checks every frame against literal 4096; `TestSSEObserverScalarScratchHardBound` checks event and JSON scalar length/capacity against literal 4096. Both fail if the corresponding bound is raised. Real TCP tests split a 12 MiB SSE comment across 4 KiB initial / 64 KiB follow-up writes and configure a 64 KiB downstream receive buffer. They receive/verify the initial 4 KiB and wait for at least one 64 KiB follow-up write to complete, then count completed fake-upstream writes until the count is unchanged for 250 ms with writes still outstanding. The 12 MiB stream exceeds the receive buffer and finite HTTP/TCP socket buffers, so this measured write-counter plateau follows confirmed traffic and cannot be explained by a producer that never started. Resuming completes all step writes and preserves the entire body byte-for-byte. RST cancellation after the same measured stall is observed upstream and finalizes once as cancelled. The narrowly scoped fakeupstream write-error signal is covered by `TestCancellationDuringResponseWrite`: on cancellation, it reports the request canceled if a blocked response write fails with request context canceled, avoiding a race with the asynchronous observer; other write errors do not report cancellation.
