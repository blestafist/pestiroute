# M10-024 — Implement explicit opt-in Antigravity managed-project onboarding and bounded LRO polling

## Outcome

Implement explicit opt-in Antigravity missing-project onboarding and bounded LRO polling per [DEC-025](../../project/DECISIONS.md#dec-025--bound-experimental-antigravity-managed-project-onboarding) and [M10-AUTH-BINDING](../M10-AUTH-BINDING.md#missing-project-onboarding-audit-m10-022). Enables safe, authorized missing-project recovery when `loadCodeAssist` indicates an absent `currentTier` and an unambiguous eligible default managed tier (with no pending terms, paid tiers, or user projects). Default remains fail-closed `auth_project_missing` with zero behavior change unless explicitly opted in via CLI flag/environment variable. See [TASKS.md](../TASKS.md#m10--google-antigravity-connector) and [M10 brief](../M10-ANTIGRAVITY.md).

## Scope

- Explicit opt-in flags and launcher configuration:
  - Add explicit onboarding opt-in flag `--allow-onboard` to `gateway admin auth continue` (and launcher environment variable `PESTIROUTE_ANTIGRAVITY_ALLOW_ONBOARD=1` forwarding `--allow-onboard` in `scripts/antigravity-auth.sh`).
  - Default remains strictly fail-closed: without explicit opt-in, missing `cloudaicompanionProject` returns `auth_project_missing` with zero outbound onboarding requests or behavior changes.
- Provenance-grounded schema & consent predicate (`internal/connector/antigravity/auth.go`):
  - Field names and types matching pinned Google CLI `types.ts`:
    - `currentTier?: GeminiUserTier | null`: must be absent or null. If present when project is missing, fails closed with `auth_project_missing` (requires user-configured project per CLI `setup.ts`).
    - `paidTier?: GeminiUserTier | null`: must be absent or null. If present, fails closed with `auth_tier_ineligible` (no billing or paid resources authorized).
    - `ineligibleTiers?: IneligibleTier[] | null`: if candidate tier is listed or `reasonCode === "VALIDATION_REQUIRED"`, fails closed with `auth_tier_ineligible`.
    - `allowedTiers?: GeminiUserTier[] | null`: must contain exactly one unambiguous eligible managed tier satisfying:
      - `id`: must be EXACTLY `"free-tier"`. Reject `legacy-tier`, `standard-tier`, or any unknown tier ID. `isDefault: true` may indicate default status among tiers, but CANNOT authorize an unknown tier ID.
      - Ambiguity: if `allowedTiers` contains 0 or >1 entries with `id: "free-tier"`, fail closed (`auth_tier_ineligible`).
      - `userDefinedCloudaicompanionProject`: must NOT be `true` (false or omitted/null accepted; if `true`, tier requires user GCP project and fails closed).
      - `hasAcceptedTos?: boolean`: if explicitly `false`, fails closed with `auth_tier_ineligible`. If omitted/absent or `true`, accepted under the operator's explicit authorization (do not demand affirmative true when wire omits it).
      - `privacyNotice?: { showNotice?: boolean }`: if `showNotice == true` requiring interactive agreement, fails closed.
      - Strict boolean validation: all optional recognized boolean fields (`userDefinedCloudaicompanionProject`, `hasAcceptedTos`, `isDefault`, `privacyNotice.showNotice`) must be valid JSON booleans if present; non-boolean types (e.g. strings/numbers) reject, never coerce.
      - Unknown metadata: unknown top-level or tier fields are ignored opaquely if bounded JSON.
- Evaluation truth table:

| Case | `currentTier` | `paidTier` | `allowedTiers` candidates | `hasAcceptedTos` | Result |
| --- | --- | --- | --- | --- | --- |
| 1. Default (no opt-in) | `null` | `null` | `[{"id":"free-tier"}]` | absent / true | FAIL-CLOSED (`auth_project_missing`, 0 dispatches) |

| 4. Duplicate free-tier | `null` | `null` | `[{"id":"free-tier"},{"id":"free-tier"}]` | absent | FAIL-CLOSED (`auth_tier_ineligible`, ambiguous) |

- Bounded onboarding request & LRO polling state machine:
  - Exactly one `POST /v1internal:onboardUser` with `tierId: "free-tier"`, `cloudaicompanionProject: undefined` (omitted in JSON), and client metadata.
  - Never retry the onboarding POST or replay ambiguous dispatch.
  - If immediate response contains `cloudaicompanionProject.id`, validate project ID and proceed to persistence.
  - If response contains LRO `name`:
    - Strict relative operation path regex: `^(?:v1internal/)?operations/[a-zA-Z0-9_\-]+$`. Reject absolute URLs, authority changes, traversal, query/fragment.
    - Poll strictly via `GET` to the same origin with bearer authorization.
    - Limits: at most 12 polls, fixed 2s interval, 30s overall context deadline.
    - Honor cancellation. Fail closed on HTTP/JSON error, LRO terminal error (`operation.error`), timeout, or malformed response.
- Invariant & persistence:
  - Project ID validated against `^[a-z][a-z0-9-]{4,28}[a-z0-9]$`.
  - Credentials persist to SQLite only after project confirmation. Any failure leaves credentials completely unsaved.
- Diagnostic canaries & pre-dispatch budget:
  - Fixed safe codes: `auth_onboarding_started`, `auth_onboarding_polling`, `auth_onboarding_failed`, `auth_tier_ineligible`, `request_budget_exceeded`. Canaries verify zero token/payload/operation-name leakage.
  - Every HTTP dispatch (discovery, onboarding POST, each GET poll) consumes 1 count from `operator_request_budgets` via `BudgetedHTTPDoer`; fails closed at ceiling (1000).
