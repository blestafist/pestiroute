# M2-001 — Specify the M2 Go binding and migration seams

## Outcome

One contract-preserving binding note fixes the interfaces needed to generalize the working M1 path. See [registry](../TASKS.md#m2--connector-api-and-conformance-baseline) and [M2](../ROADMAP.md#m2--connector-api-and-conformance-baseline).

## Read First

- [Component lifecycle](../CONTRACT.md#component-descriptor-and-lifecycle), [Connector operations](../CONTRACT.md#connector-contract), [Adapter operations](../CONTRACT.md#protocol-adapter-contract).
- [Scoped services](../CONTRACT.md#usage-and-scoped-runtime-services), [versioning](../CONTRACT.md#versioning-and-change-control), [M1 handoff](M1-027.md#completion-evidence).
- `internal/core/{execution,dispatch}.go`, `cmd/gateway/main.go` component wiring; inspect only public signatures in the existing Adapter and Connector.

## Scope

- Write `docs/implementation/M2-BINDING.md`: map every v1 operation to a concrete Go signature, owner, and error/unknown representation. Reuse existing envelope/frames/errors; choose the smallest shared package boundary with no concrete imports.
- Define descriptor/API-version validation, lifecycle concurrency, capability/model/account scope, and support-operation results. Define invocation-scoped credential, transport, and logging services; auth storage/refresh remains M3.
- Fix route identity matching, conflicting-route behavior, static model/capability declarations and their evidence scope. Specify a minimal startup JSON extension and legacy single-target mapping; keep inference loopback-only and native-only.
- Define attempt record/finalizer ownership and Complete-to-EOF validation before terminal success, including malformed trailing frames and bounded cancellation. Link the note from STACK. Stop at design; any semantic change needs an ADR and synchronized specifications.

## Acceptance

- [ ] Every signature traces to v1, including Models, EstimateUsage and Authenticate; unavailable operations have explicit unsupported/unknown results.
- [ ] Package ownership, startup compatibility and lifecycle/finalization walkthroughs are concrete enough to refine each dependent card without inventing behavior.
- [ ] No new LLM schema, frame variant, automatic retry, secret persistence, or released capability claim is introduced.

## Verification

From repository root: Manually trace success, failed Init, pre-Head rejection, cancellation, and Complete followed by an illegal frame through the proposed signatures. Map signatures to v1 sections; check local links/anchors and run `git diff --check`. Record decisions and unresolved conflicts, not implementation claims.

## Open Questions / Blocker

None. Choosing the concrete binding is this planning deliverable; an actual conflict with v1 must be resolved through the project ADR process before downstream execution.

## Completion Evidence
