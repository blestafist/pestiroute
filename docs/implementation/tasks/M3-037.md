## Scope

- Implement explicit ordered target groups for an exact native protocol/model route, evaluating candidate targets with the shared authorization/account/capability predicate (`CandidateAuthorization`, `AccountAuthorizer`, `EligibilityCandidate`) and candidate-specific body/header limits.
- Implement the approved trusted northbound statefulness/affinity gate: Adapter (`internal/adapter/responses/decode.go`) detects statefulness (e.g. `previous_response_id`) and marks trusted request metadata; Core enforces that session-bound requests or requests with unknown affinity require a singleton target route and fail closed before dispatch if multiple targets are configured.
- Reject duplicate or conflicting targets in route configuration; ensure candidate iteration is deterministic and exhausted selection does not cycle.
- Wire validated multi-target route groups into protected gateway startup (`cmd/gateway/protected_startup.go`), lifting the temporary single-target startup validation restriction.
- Preserve original payload bytes; no alias rewriting, weighted balancing, dynamic discovery or provider-specific routing.

- [x] Singleton/stateful (e.g. `previous_response_id`) and unknown-affinity requests cannot select another account/backend and fail closed if multiple targets are configured; forged client metadata cannot create authorization or retry permission.

## Completion Evidence

Implemented `Dispatcher.AuthorizedCandidates` over exact protocol/model candidate groups. It preserves YAML order and returns only candidates passing one immutable key-policy snapshot, current account/connector authorization, candidate-specific body/header limits, initialized component/protocol checks, and supported request/route capabilities (including route-declared requirements); it performs no estimate, reservation, or execution. Protected startup normalizes targets, connector-owned limits and route requirements into candidate groups and rejects duplicate/conflicting target identities. `Dispatcher.Execute` continues to execute only the primary route. Core derives body size from the opaque payload byte length; trusted Responses Decode reports original ingress-header bytes before filtering, with zero treated as unavailable and target header limits failing closed.

Responses affinity classification preserves body bytes and ignores client-supplied metadata. The official [Create a model response schema](https://developers.openai.com/api/reference/resources/responses/methods/create) defines `background` as optional boolean-or-null (default false); false/null/omitted add no affinity, while true is unknown because background execution is not guaranteed portable across backends ([ARCHITECTURE](../../project/ARCHITECTURE.md#stateful-responses)). The schema defines `store` as boolean-or-null (default true) and says it stores the generated response for later retrieval, not that it references an inbound resource. Accordingly omitted, true, false and null are known stateless for this request; malformed types are unknown. `previous_response_id` and string/object `conversation` IDs name inbound resources and are session-bound; null means no inbound reference. Protected multi-target HTTP coverage verifies prior-response requests dispatch to neither backend, while `store:true` and ordinary requests execute primary only. M3-004, M3-019, and M3-020 were confirmed DONE before start.
