# M3-007 — Create virtual-key and policy schema

## Outcome

Add versioned migration 3 to the SQLite storage migration engine establishing `key_policies` and `virtual_keys` relational schema, integrity constraints, and indexes. This is one bounded deliverable in the [M3 registry](../TASKS.md#m3--access-accounts-and-accounting) toward [M3](../ROADMAP.md#m3--access-accounts-and-accounting).

## Scope

- Add version 3 to `schemaMigrations` in `internal/storage/sqlite/migrate.go` creating:
  - `key_policies` table: `id TEXT NOT NULL`, `revision INTEGER NOT NULL CHECK (revision >= 1)`, `enabled INTEGER NOT NULL DEFAULT 1 CHECK (enabled IN (0, 1))`, `models TEXT NOT NULL`, `connectors TEXT NOT NULL`, `rpm INTEGER NOT NULL CHECK (rpm >= 0)`, `tpm INTEGER NOT NULL CHECK (tpm >= 0)`, `created_at INTEGER NOT NULL`, with `PRIMARY KEY (id, revision)`.
  - `virtual_keys` table: `id TEXT PRIMARY KEY`, `key_id TEXT NOT NULL UNIQUE`, `digest TEXT NOT NULL UNIQUE`, `policy_id TEXT NOT NULL`, `policy_revision INTEGER NOT NULL`, `revision INTEGER NOT NULL DEFAULT 1 CHECK (revision >= 1)`, `enabled INTEGER NOT NULL DEFAULT 1 CHECK (enabled IN (0, 1))`, `revoked INTEGER NOT NULL DEFAULT 0 CHECK (revoked IN (0, 1))`, `created_at INTEGER NOT NULL`, `revoked_at INTEGER`, with `FOREIGN KEY (policy_id, policy_revision) REFERENCES key_policies(id, revision) ON DELETE RESTRICT`.
  - Indexes: `idx_virtual_keys_digest ON virtual_keys(digest)`, `idx_virtual_keys_policy ON virtual_keys(policy_id, policy_revision)`.
- Use UTC Unix-millisecond integers (`INTEGER`) for `created_at` and `revoked_at` per M3-STORAGE.md.
- Enforce non-negative integer RPM and TPM limits; note that per-route conservative token budgets belong to route YAML config per M3-CONFIG.md and M3-RUNTIME.md, not key-policy columns.
- Ensure schema compatibility with the existing migration runner, preserving WAL, `synchronous=FULL`, foreign keys, and 500 ms busy timeout.
- Explicit limits: schema migrations, indexes, and DDL checks only; no virtual key generation/verification/revocation logic (belongs to M3-012); no policy repository methods (belongs to M3-013); no CLI commands (belongs to M3-014); no request/attempt tables (belongs to M3-008); no plaintext keys or secret hashing code.

## Acceptance

- [x] Version 3 migration applies atomically via `Migrate` on top of version 2 or fresh database, recording version 3 in `schema_migrations`.
- [x] Duplicate primary keys in `key_policies` (`(id, revision)`) or `virtual_keys` (`id`), duplicate public `key_id`, or duplicate `digest` values are rejected by uniqueness constraints.
- [x] Foreign key constraints enforce referential integrity: inserting a virtual key with nonexistent `(policy_id, policy_revision)` fails, and deleting a policy referenced by a virtual key fails under `ON DELETE RESTRICT`.
- [x] Disabling a key or policy (`enabled = 0`) or revoking a key (`revoked = 1`, `revoked_at` set) retains records and preserves referential integrity without deleting policy or key history.
- [x] Negative RPM (`rpm < 0`), negative TPM (`tpm < 0`), non-positive revisions (`revision < 1`), and invalid boolean flags (`CHECK (enabled IN (0, 1))`, `CHECK (revoked IN (0, 1))`) are rejected by CHECK constraints.
- [x] Timestamps use `INTEGER` UTC Unix milliseconds (`created_at`, `revoked_at`).
- [x] No plaintext key or secret columns exist in table definitions; only cryptographic digest is stored.
- [x] `PRAGMA foreign_key_check` passes with zero violations across sample policies and virtual keys.
- [x] Failed migration statement in a test migration rolls back atomically, leaving the database at version 2 without partial DDL.
- [x] Existing migration idempotency and future-schema refusal tests continue to pass with the new migration version.
