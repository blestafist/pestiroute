# M5.2-008 — Implement explicit upstream authentication policy

## Outcome

Implement explicit upstream authentication handling (`none` and `bearer`) for the local-runtime Connector path in `internal/connector/responses`, allowing local endpoints (Ollama, vLLM, llama.cpp) to operate without upstream authorization headers while supporting authenticated endpoints without credential fabrication or bypassing client virtual-key checks. One bounded result in [the M5.2 registry](../TASKS.md#m52--local-runtime-connectors), under [ROADMAP M5.2](../ROADMAP.md#m52--local-runtime-connectors).

## Scope

- Extend `internal/connector/responses` with explicit upstream auth handling for the local-runtime connector path:
  - Add configuration support for explicit auth mode: `none` or `bearer`.
  - When auth mode is `none`, transport omits the upstream `Authorization` header completely; connector execution does not request or require credentials from `services.Credentials`.
  - When auth mode is `bearer`, transport obtains only the selected account's scoped credential via `services.Credentials.Get(ctx, "bearer")` and adds `Authorization: Bearer <credential>`. If `services.Credentials` is nil or the credential is missing/empty/error, fail pre-dispatch with `CategoryUnauthenticated`.
  - Update `Transport.Request` / `Transport.Do` (or parameterize request construction) so header generation is controlled by explicit auth mode rather than unconditionally adding bearer auth.
  - Connector descriptor reports the local runtime category and its configured/supported auth methods (`[]string{"none"}` or `[]string{"bearer"}`).
  - Strict initialization: reject invalid, unrecognized, or empty auth modes; reject unknown fields and trailing configuration data.
  - Prevent client header leakage: sanitize/block incoming client metadata headers (`Authorization`, `Proxy-Authorization`) so they cannot leak upstream or override the configured auth policy.
- Explicit limits:
  - No inferred auth mode from destination host/IP (e.g., `localhost` or `127.0.0.1`), port, model name, or provider name.
  - No placeholder/generated token creation, client-header credential fallback, or connector-owned secret persistence.
  - Preserve client-side virtual-key authentication on ingress untouched.
  - Preserve the existing native `pestiroute.responses.native` connector (`ConnectorType: "api"`, `AuthMethods: []string{"bearer"}`) and existing Anthropic/Codex behavior without modification to their defaults.
  - YAML configuration schema/route composition changes in `cmd/gateway/yaml_config.go` are deferred to M5.2-013.
  - No real backend calls, live runtime installation, or container execution.

## Acceptance

- [x] Explicit `none` auth mode: upstream HTTP request omits `Authorization` header completely; execution proceeds without requesting or requiring credentials from `services.Credentials`.
- [x] Explicit `bearer` auth mode: upstream HTTP request includes `Authorization: Bearer <credential>` using only the selected account's credential from `services.Credentials.Get(ctx, "bearer")`.
- [x] Missing credential in `bearer` mode: execution fails pre-dispatch with `CategoryUnauthenticated` when credentials service is unavailable or credential retrieval fails/is empty.
- [x] Client header isolation: client-supplied `Authorization` or `Proxy-Authorization` headers in request metadata are stripped/blocked and never forward upstream regardless of auth mode.
- [x] Configuration validation: initialization strictly validates auth mode (`none` or `bearer`), rejecting invalid, empty, or unknown auth mode values, unknown JSON fields, and trailing data.
- [x] Native backwards compatibility: existing `pestiroute.responses.native` connector behavior is unchanged (reports API category and bearer auth, and requires bearer credentials). Ingress virtual-key enforcement is unaffected.
