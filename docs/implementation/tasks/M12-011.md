# M12-011 — Complete live Usage filtering, pagination and attempt details

## Outcome

Make the real ledger navigable beyond the initial 50 requests using the accepted
M11 API. This closes the functional gap before M12-009 presentation work.

## Read First

- [WebUI outcome](../M12-WEBUI.md), [registry](../TASKS.md).
- `web/src/api.ts`, live Usage in `web/src/App.tsx` and its tests.
- `docs/api/admin.openapi.yaml` usage endpoints; `internal/admin/read.go`.

## Scope

- Add account/key and since/until controls supported by the existing endpoints;
  use server limit/offset/total for request pagination and bounded page sizes.
- Preserve non-secret filters in the URL, reset offset on filter changes, validate
  date bounds, and retain filters after refresh/navigation and errors.
- Align summary and request filters. Join attempt detail by request ID when
  requested; display ordered attempts, targets, nullable usage and error/fallback
  evidence without inventing a fallback status or exposing raw payloads.
- Prevent stale/out-of-order fetch results from overwriting newer filter results.
- Do not invent model/outcome server filters. Keep them absent or explicitly
  page-local until a separately scoped API extension is accepted. Never label a
  filtered page as the whole ledger.
- Only change `web/**` and this lane's documentation. No backend/schema changes.

## Acceptance

- [ ] A mocked HTTP ledger with more than 50 requests can be traversed with
  correct limit/offset requests and server totals; filter changes reset paging.
- [ ] Account/key/date filters reach the existing API and matching summary;
  invalid dates block dispatch and retain input.
- [ ] Unknown token values stay unknown; expanded details use the selected
  request's attempts, including a multi-attempt fixture.
- [ ] Delayed older responses cannot replace the current query's results;
  errors retain navigation state and 401 clears the operator session.
- [ ] Component tests cover these observable cases without provider calls.
