# M3-025 — Persist dispatch intent before upstream execution

## Outcome

Durable transition of attempt state from `reserved` to `intent` before upstream execution (`Execute`), ensuring SQL durability acknowledgement is required to release dispatch and distinguishing provably not dispatched attempts from dispatch-uncertain attempts without remote provider assumptions. This is one bounded deliverable in the [M3 registry](../TASKS.md#m3--access-accounts-and-accounting) toward [M3](../ROADMAP.md#m3--access-accounts-and-accounting).

## Scope

- In `internal/storage/sqlite`:
  - Enforce atomic attempt state transition from `reserved` to `intent` via `Ledger.RecordDispatchIntent(ctx context.Context, id string, at time.Time) error`:
    - Verify that the target attempt exists, belongs to an `admitted` request, and is in `reserved` state before updating to `intent`.
    - Record `dispatched_at` timestamp in UTC Unix milliseconds.
    - Idempotency: identical repeated intent calls (matching attempt ID and timestamp) succeed cleanly without duplicating attempts or reservations; conflicting states (e.g. non-admitted request, missing attempt, terminal state) return `ErrLedgerConflict` or `ErrLedgerNotFound`.
    - Durable SQL write acknowledgement: returns only after transaction/update commits under SQLite durability policy.
- In `internal/core` (or execution coordination seam):
  - Establish the execution gate / runner contract (e.g., `DispatchIntentRecorder` or `IntentGate` / gated execution helper) ensuring `Connector.Execute` (or `Target.Execute`) is invoked only after durable SQL intent acknowledgement.
  - Enforce failure boundaries: if intent persistence fails, times out, or the context is cancelled before commit, zero `Execute` calls are made to upstream; the attempt remains in `reserved` (provably not dispatched) state.
  - Enforce uncertain delivery boundaries: once intent is committed, any subsequent failure or abrupt process termination leaves the attempt in `intent` (dispatch-uncertain) state, recoverable conservatively without claiming remote cancellation or triggering automatic replay.
- Explicit limits:
  - Does not implement terminal settlement, token overage, or reservation release (reserved for [M3-026](M3-026.md)).
  - Does not wire end-to-end admission, fallback routing, and reconciliation into `Dispatcher.Execute` or HTTP handlers (reserved for [M3-027](M3-027.md)).
  - Does not implement startup recovery scan / sweep (reserved for [M3-029](M3-029.md)).
  - Does not add distributed transactions or provider-specific retry policies.

## Acceptance

- [x] Attempt transition from `reserved` to `intent` updates `attempts.state = 'intent'` and records `dispatched_at`; missing attempts return `ErrLedgerNotFound`, and attempts on non-admitted requests or in non-reserved states return `ErrLedgerConflict`.
- [x] A failed, timed out, or cancelled intent write causes zero `Execute` calls to the target/connector and leaves the attempt in `reserved` state.
- [x] Repeated identical intent recording calls are idempotent and do not duplicate requests, attempts, or reservations.
- [x] File-backed connection close and reopen preserves and distinguishes admitted-not-dispatched (`reserved`) from dispatch-uncertain (`intent`) attempt records without data loss or remote status invention.
