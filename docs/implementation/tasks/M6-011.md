## Scope

- Runtime-issued invocation identity, process epoch, callback correlation, admission bounds and revocation only.
- Do not implement credential, HTTP, log service semantics or Execute stream framing; separate tasks own those.

## Acceptance

- [x] Bind all invocation/callback traffic to host-issued invocation ID and current process epoch; child-provided account cannot confer authority.
- [x] Reject stale epoch, unknown/completed invocation, duplicate call IDs and cross-invocation callbacks.
- [x] Enforce four concurrent invocation and callback outstanding limits; cancellation/revocation returns callback admission without waiting for outstanding callbacks; restart never reuses epoch.

## Completion Evidence

Implemented a host-owned per-Connector-epoch invocation registry with random 128-bit IDs, host-selected account association, four active invocation admission, callback correlation and 8/32 outstanding bounds. Callback leases derive authority from the matching live invocation; cancellation, failed Init and Close revoke authority and return admission without waiting on callback work. Epoch creation remains the existing fresh `newEpoch` cryptographic-random handshake behavior.

Deterministic registry tests cover concurrent account isolation, wrong/stale epoch, unknown/revoked invocation, duplicate and cross-invocation call IDs, admission bounds, and parent cancellation with all 8/32 callback slots outstanding. Cancellation promptly revokes those callbacks, frees invocation/callback admission, and makes late-result authorization fail without waiting for callback completion. These are callback-registry checks, not transport data-queue/control-lane saturation tests; M6-020 owns those. Transport-level Execute/reverse-service dispatch is not part of this slice; later operation-bridge work consumes the registry.
