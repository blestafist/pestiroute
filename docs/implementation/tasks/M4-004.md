## Outcome

Declare Responses format support for translation routes. One bounded deliverable in the [M4 registry](../TASKS.md#m4--first-translation-connector)
toward the original [M4](../ROADMAP.md#m4--first-translation-connector).

## Read First

- [Protocol Adapter boundary](../CONTRACT.md#protocol-adapter-contract).

## Scope

- Allow the existing Responses Adapter to describe client-format capabilities in a trusted translation scope (`core.ModeTranslation`) where appropriate, alongside `core.ModeNative`.
- Keep backend capability claims strictly in the Connector; the Adapter only declares client-format capabilities (`llm.streaming`, `llm.tools`, `llm.tools.parallel`, `llm.reasoning`, `llm.structured_output`, `llm.vision`, `llm.audio`) for valid scopes.
- Retain opaque Decode, required-capability extraction, generic Encode, HTTP status mapping, and native extensions. Introduce no Responses-to-Messages translation logic or provider names.

## Acceptance

- [x] Responses Adapter reports supported format capabilities for valid `core.ModeTranslation` scopes matching protocol `responses` and non-empty `Model`.
- [x] Uninitialized or closed Adapter, empty model, mismatched protocol, or invalid mode return unknown/empty capabilities.
- [x] Core candidate eligibility requires both Adapter and Connector support; missing or unknown Connector capabilities reject candidate selection under translation mode.
- [x] Native request decoding, exact byte preservation, error mapping, and existing invalid-input behavior remain intact with zero provider imports or names.
