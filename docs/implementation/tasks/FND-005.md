# FND-005 — Select the M1 compatibility baseline

## Outcome

Choose one concrete Responses-native backend/model and one real client/version for the [M1 smoke gate](../ROADMAP.md#m1--transparent-responses-proxy), with a repeatable tool and parallel-tool scenario. See the [registry row](../TASKS.md#m0--foundation). The choice lets M1 plan a specific compatibility check without implying that it already passes.

## Read First

- [M1 acceptance](../ROADMAP.md#m1--transparent-responses-proxy) and [first vertical slice](../ROADMAP.md#first-vertical-slice).
- [Reference research rules](../REFERENCES.md#how-to-use-sources), [source/runtime evidence](../REFERENCES.md#connector-research-template), and [direct versus gateway verification](../TESTING.md#direct-versus-gateway).
- [Native mode boundary](../CONTRACT.md#connector-contract) only where needed to distinguish a native Responses endpoint from translation or a subscription client protocol.

## Scope

- Research candidate endpoints using current official backend API documentation and client source or documentation at a named version/revision. Choose exactly one primary backend endpoint and model that can accept Responses requests, stream, and support the intended tool scenario according to source evidence. Identify its auth/access prerequisites and any material feature gaps. A public OpenAI-compatible label alone is insufficient evidence of Responses support.
- Choose one specific real client and version/revision, preferably the agent client named in [project success criteria](../../project/README.md#success-criteria) if it exposes a suitable Responses flow. Confirm how its endpoint/base URL can be pointed at a gateway and how it issues and continues tool calls; do not equate a subscription backend protocol with the official public API. If that client cannot meet the gate, record the source evidence and choose another concrete client.
- Add a compact `## M1 Compatibility Baseline` section to [REFERENCES.md](../REFERENCES.md). Record source URLs, retrieval date and pinned versions; endpoint, model and client; required access and configuration with no credential values; direct and gateway invocation steps; the tool/parallel-tool round-trip and invariants (IDs, ordering, completion, first chunk, cancellation); and the expected location for sanitized traces. State what remains unknown until a real run.
- Do not add connector code, fixture recordings, credentials, a capability declaration of `supported`, or a live smoke result. Keep real inference execution and direct-versus-gateway comparison in M1.

## Acceptance

- [ ] A reviewer can find a concrete backend endpoint/model and client version/revision, with source evidence for Responses, streaming, tools and parallel calls or an explicit gap needing validation.
- [ ] The procedure says how to run the same model, client, settings and tool workflow directly and through the future gateway, and what observable events/IDs to compare rather than comparing generated text.
- [ ] Authentication prerequisites, access/cost needs and the absence or presence of available access are explicit; no secret or private payload is included.
- [ ] Source evidence is separated from unrun runtime claims. Any uncertain field or behavior is marked unknown with a specific M1 check; the note does not imply support for all Responses features.
- [ ] Another worker can reproduce the intended steps once M1's gateway path exists, or the note identifies the precise missing prerequisite and a viable alternative.

## Verification

Manual, reproducible review from the repository root: open the added `M1 Compatibility Baseline` section, follow every source link to its named document/revision and verify the endpoint, client configuration, and stated tool behavior against it. Walk through the written direct/gateway procedure and check that it names the same model and settings, tool result continuation, parallel call IDs, streamed first chunk, and cancellation observation; verify that real gateway-dependent steps are labeled for M1 rather than reported as passed. Search the note for secret values/private traces and run `git diff --check`. Record the exact source URLs/revisions, review date, and any conflicting claims in Completion Evidence. This is a source-and-procedure review, not a live smoke test or an automated test suite.
