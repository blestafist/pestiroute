# M3-020 — Load strict versioned M3 YAML

## Outcome

Load strict versioned M3 YAML (`version: 1`) and normalize startup configuration into typed internal structures while preserving legacy single-target JSON and M2 topology JSON compatibility strictly on numeric loopback. This is one bounded deliverable in the [M3 registry](../TASKS.md#m3--access-accounts-and-accounting) toward [M3](../ROADMAP.md#m3--access-accounts-and-accounting).

## Scope

- Pin `gopkg.in/yaml.v3` v3.0.1 in `go.mod`/`go.sum` and ensure offline check compatibility with `./scripts/check.sh` (`GOPROXY=off GOSUMDB=off`).
- Implement the bounded strict YAML loader (1 MiB limit, UTF-8 single document) in `cmd/gateway` enforcing:
  - Root schema version exactly `1`.
  - Exactly the seven allowed root keys: `version`, `server`, `storage`, `secrets`, `connectors`, `routes`, `policies`.
  - Rejection of unknown fields at every level via strict decoding (`KnownFields(true)` and AST node traversal for duplicate keys).
  - Rejection of YAML aliases (`*alias`), anchors (`&anchor`), merge keys (`<<`), explicit nulls, multi-documents, and type coercion.
  - Validation of `server`: `listen` TCP address, positive `max_request_bytes`, positive Go duration `shutdown_timeout`.
  - Validation of `storage`: `driver` strictly `sqlite`, non-empty `path`.
  - Validation of `secrets`: non-empty `master_key_file` path.
  - Validation of `connectors`: unique non-empty `id`, `kind: connector`, `implementation: pestiroute.responses.native`, unique `protocols: [openai.responses.v1]`, and connector-owned `settings` (`base_url` HTTPS or loopback HTTP, `upstream_protocol: openai.responses.v1`, `mode: native`, present non-empty `credential_env`, positive limits and positive duration timeouts).
  - Validation of `routes`: unique non-empty `id`, `protocol: openai.responses.v1`, `mode: native`, non-empty exact `model`, `adapter: pestiroute.responses.native`, `policy` referencing top-level `policies`, `budget` (`unknown_estimate: reject` or `unknown_estimate: reserve` with positive `conservative_tokens`), optional unique `requirements`, non-empty ordered `targets` (`connector` and `account`), and optional `retry` (`max_attempts >= 1`, default 1; positive duration `deadline` required when `max_attempts > 1`).
  - Validation of `policies`: non-empty mapping of local policy references to SQLite key-policy IDs.
  - Cross-referencing: each route target references a declared connector `id`; each route `policy` references a declared name in top-level `policies`. Target accounts and policy IDs are validated syntactically as non-empty identifiers.
- Compatibility isolation:
  - Preserve legacy single-target JSON and M2 topology JSON loaders exclusively on numeric loopback (`127.0.0.1` or `::1`).
  - Format selection is explicit; any failure in protected YAML fails closed immediately and never degrades to JSON development mode.
- Explicit limits:
  - YAML loading, schema validation, and normalization to typed configuration structures only.
  - Full runtime composition with SQLite and live dispatch belongs to [M3-030](M3-030.md).
  - Fallback candidate execution belongs to [M3-037](M3-037.md).
  - Dynamic topology reload is strictly out of scope.

## Open Questions / Blocker

**Normative startup blocker:** `M3-CONFIG.md#startup-isolation-and-compatibility` requires protected startup to verify the referenced SQLite accounts and key policies (including account ownership/enabled state) and abort before readiness on any failure. This bounded loader can validate only connector IDs and policy-reference names declared in YAML plus non-empty persistent IDs; it has no persistent catalog/runtime startup binding. Protected `run` therefore rejects even valid YAML with an explicit M3-030 blocker instead of serving without those checks or falling back to JSON. Unblock when M3-030 supplies SQLite-backed reference validation and protected runtime composition, then re-run the protected startup/readiness check. Do not remove the fail-closed guard as a workaround.
