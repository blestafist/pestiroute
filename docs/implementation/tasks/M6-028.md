# M6-028 — Verify concurrent external account isolation

## Outcome

Verify concurrent external account isolation across parallel client requests, child connector instances, and process epochs in protected gateway execution. Prove that concurrent requests across distinct accounts/instances cannot leak or exchange credentials, cross-contaminate response frames, or hijack callback authority, and that stale-process epoch callbacks fail closed. See [registry](../TASKS.md#m6--external-plugin-runtime) and [milestone](../ROADMAP.md#m6--external-plugin-runtime).

## Scope

- Deterministic integration tests in `cmd/gateway/` (and/or `internal/connector/external/`):
  - Concurrent multi-account execution: parallel requests across distinct virtual keys, accounts, and external connector instances/processes verify zero credential cross-talk and isolated loopback upstream deliveries.
  - Callback authority & host-services validation: verify host-issued invocation ID and process epoch prevent cross-invocation/cross-account credential retrieval (child requesting credentials for another account fails closed).
  - Stale-process / epoch race tests: verify callbacks or frames from a crashed/terminated child epoch are rejected with `errInvocationStale` / fail-closed status and cannot inject data or hijack active invocations in a new epoch.
  - Concurrency & race safety: run tests under `go test -race` with clean process, goroutine, and socket cleanup.
- Limits:
  - Cross-connector unified conformance suite belongs to M6-029.
  - Offline run procedure documentation belongs to M6-030.
  - Integration guide belongs to M6-031.
  - Core authorization / virtual-key policy engine is unchanged; verifies external connector process boundary integration.

## Acceptance

- [x] Parallel requests under distinct accounts/virtual keys execute concurrently across external connector processes without cross-account credential leakage or frame mixing.
- [x] Child callback requesting credentials for a different account than the host-bound invocation is denied fail-closed.
- [x] Callbacks or responses bearing a stale or mismatched process epoch fail closed and cannot mutate or complete active invocations in a newer generation.
- [x] Gateway accounting and SQLite ledger settle per-account token usage accurately without cross-account attribution errors or dangling reservations.
- [x] Tests pass under `go test -race` with zero leaked processes, goroutines, or IPC sockets.

Audit assertions require the expected denied/injected markers and forbid `foreign-credential-accepted`, `spoofed-invocation-accepted`, and `stale-epoch-accepted`. For both concurrent phases the fixture waits for same-phase identities from both children before issuing cross-account callbacks. After restarting account A's child, a second upstream arrival gate holds both A/B requests; A's stale callback/frame is rejected while B remains gated, then B is released and succeeds. A then succeeds on the replacement's current epoch. Every generation PID/PGID is retained, checked for group disappearance and `/proc` reaping at replacement and cleanup; child socket directories are checked after shutdown. SQLite evidence checks both account attribution, settled successful usage, conservative finalization of the interrupted stale-frame request, and absence of dangling reservations. Gateway logs, fixture audit, and SQLite are checked for plaintext credentials/virtual-key secrets. Cleanup releases every gate before closing the server/components.
