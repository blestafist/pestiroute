# M3-016 — Add virtual-key and policy administration commands

## Outcome

Add virtual-key and policy administration commands to the local CLI (`cmd/gateway`), allowing operators to provision and update immutable-revision key policies, issue virtual keys with one-time raw secret disclosure, query safe metadata, perform optimistic policy updates, and revoke keys monotonically without starting a network listener, leaking secret tokens, or introducing implicit account/route scoping. This is one bounded deliverable in the [M3 registry](../TASKS.md#m3--access-accounts-and-accounting) toward [M3](../ROADMAP.md#m3--access-accounts-and-accounting).

## Scope

- Extend `cmd/gateway` administration commands dispatched under `gateway admin [flags] <subcommand> [args]`:
  - Policy administration subcommands:
    - `policy create [--id <id>] [--models <m1,m2,...>] [--connectors <c1,c2,...>] [--rpm <N>] [--tpm <N>]`: provisions a key policy (revision 1, default enabled) via `sqlite.KeyPolicies.Create`. If `--id` is omitted, generates a random ID. Omitted models/connectors default to empty lists `[]` (fail-closed deny all, stored as JSON array `'[]'`). Rejects negative limits or empty string items.
    - `policy get <id> [--revision <N>]`: displays policy safe metadata (`id`, `revision`, `enabled`, `models`, `connectors`, `rpm`, `tpm`, `created_at`). When `--revision` is omitted or 0, retrieves the latest revision via `sqlite.KeyPolicies.GetLatest`; otherwise retrieves exact revision via `sqlite.KeyPolicies.Get`.
    - `policy list [--enabled=true|false]`: lists the latest revision of policies matching the optional filter via `sqlite.KeyPolicies.List`.
    - `policy update <id> --expected-revision <N> [--models <m1,m2,...>] [--connectors <c1,c2,...>] [--rpm <N>] [--tpm <N>] [--disabled]`: appends a new immutable revision (`expectedRevision + 1`) via `sqlite.KeyPolicies.Update`. Enforces optimistic CAS; fails with `ErrKeyPolicyRevisionMismatch` if stored revision does not match `--expected-revision`.
  - Virtual-key administration subcommands:
    - `key create --policy <policy_id> [--policy-revision <N>]`: issues a high-entropy virtual key via `sqlite.VirtualKeys.Create`. If `--policy-revision` is omitted or 0, resolves the latest revision of the policy via `sqlite.KeyPolicies.GetLatest`. Prints the newly issued raw secret (`prv_...`) along with safe metadata (`id`, `key_id`, `policy_id`, `policy_revision`, `revision`, `enabled`, `created_at`) to `stdout` exactly once.
    - `key get <id>`: displays safe key metadata by internal ID or public identifier (`key_id`) via `sqlite.VirtualKeys.Get` or `sqlite.VirtualKeys.GetByKeyID`. Raw secret is never printed.
    - `key list [--policy <policy_id>] [--enabled=true|false] [--revoked=true|false]`: lists virtual keys matching optional filters via `sqlite.VirtualKeys.List`.
    - `key revoke <id>`: monotonically revokes a virtual key via `sqlite.VirtualKeys.Revoke`. Revocation increments revision, records `revoked_at`, and is permanent.
    - `key update-policy <id> --policy <policy_id> [--policy-revision <N>] --expected-revision <N>`: updates the key's policy reference via `sqlite.VirtualKeys.UpdatePolicy`. Enforces optimistic CAS against `--expected-revision`. Fails if the key is revoked or revision mismatches.
  - Safe one-time disclosure and isolation:
    - Raw secret (`prv_...`) is printed strictly to stdout upon successful `key create` output and nowhere else.
    - On creation failure, errors, logs, stderr, and subsequent `key get`, `key list`, `key revoke`, or `key update-policy` outputs, no secret token is printed. Only public identifier (`key_id`, e.g. `prk_...`), internal `id`, and safe metadata are printed.
    - No raw secret export command is provided; stored digests cannot be reversed.
  - Operational conventions:
    - Global flags `--db` and `--master-key` are enforced; master key regularity, mode (`0600`), and length are verified via `crypto.LoadMasterKey`.
    - Requires complete current schema before key/policy operations; unmigrated, partial, or future schemas fail closed. Database handles cleanly close on all exit paths.
- Explicit limits:
  - No implicit account or route scope: virtual keys identify policies, which restrict models and connectors; virtual keys and policies do not bind to specific accounts, credentials, or YAML route configurations.
  - Runtime request authentication and policy snapshot enforcement belong to [M3-018](M3-018.md) and [M3-019](M3-019.md).
  - Protected YAML configuration loading belongs to [M3-020](M3-020.md).
  - Usage inspection subcommands belong to [M3-031](M3-031.md).
  - Core runtime packages (`internal/core`) remain untouched.

## Acceptance

- [x] `gateway admin policy create`, `get`, `list`, and `update` operate against a real file-backed SQLite database across separate invocations, enforcing schema validation and JSON serialization.
- [x] Policy updates enforce optimistic revision checks (`--expected-revision`), write a new immutable revision row, and fail with a classified error leaving historical revisions intact on revision mismatch.
- [x] `gateway admin key create` provisions a virtual key referencing a valid policy revision, printing the issued raw secret (`prv_...`) to stdout exactly once.
- [x] On failed key/policy creation or update, no secret is printed, stderr receives a classified error, and storage is not partially mutated.
- [x] Subsequent key operations (`key get`, `key list`, `key revoke`, `key update-policy`) output safe metadata only (`id`, `key_id`, policy references, revisions, timestamps); raw secret is never displayed, logged, or retrievable.
- [x] Monotonic key revocation (`key revoke`) sets `revoked = 1`, records `revoked_at`, increments revision, and permanently blocks re-enabling or policy mutation across restarts.
- [x] Optimistic policy reassignment (`key update-policy`) updates the policy reference with CAS checking, failing on stale revision or already-revoked key.
- [x] No implicit account or route scope: virtual key and policy administration strictly respects model and connector boundaries without embedding account or route bindings.
- [x] Subcommands enforce required `--db` and `--master-key` flags, validate master key permissions/regularity, fail closed on unmigrated/future schema, and close database handles cleanly.
