# M2-026 — Add error, usage and no-replay conformance cases

## Outcome

Common metadata keeps failures, unknown accounting and replay safety separate from opaque error bodies. Both native-loopback and scripted connector suites verify pre-Head rejections, non-200 HTTP bodies, 200-declared failures, nullable usage counter separation, and single-attempt execution without hidden replays. See [registry](../TASKS.md#m2--connector-api-and-conformance-baseline) and [M2](../ROADMAP.md#m2--connector-api-and-conformance-baseline).

## Scope

- Expand `internal/conformance/` (e.g. `internal/conformance/error_usage_test.go`) with conformance scenarios executed across both native-loopback and scripted connector fixtures, through direct invocation and Core dispatch:
  - Pre-Head failure: connector returns `*GatewayError` before any stream frames (e.g. credential rejection, immediate connection/transport failure); assert classified category, non-safe retry disposition, no stream frames delivered, and Core records exactly one uncommitted failed attempt (`Committed == false`, `Outcome == OutcomeFailed` or `OutcomeCancelled`).
  - Head and body rejection: upstream HTTP 4xx/5xx rejections (e.g. 400 Bad Request, 401 Unauthorized, 403 Forbidden, 429 Rate Limited, 503 Service Unavailable) deliver `Head` with classified `GatewayError` and byte-preserved response bodies, terminating with `Complete(failed)`:
    - 429 and 503 set `Retryable == true` and parsed `RetryAfter` (when header present), but preserve `RetryDisposition == RetryUnknown` (never safe without explicit connector assertion).
    - 400, 401, 403 have `Retryable == false` and non-safe disposition.
    - Error response body bytes are preserved verbatim (opaque error byte preservation).
  - HTTP-200 declared failure: upstream returns HTTP status 200 with declared failure in payload (e.g. Responses JSON with `status: "failed"` or SSE terminal failure event):
    - HTTP 200 status alone never yields `OutcomeSucceeded`; terminal Complete outcome is `OutcomeFailed` with classified `GatewayError`.
    - Native failure payload bytes remain preserved.
  - Usage accounting invariants:
    - Nullable counters: missing counters remain `nil` (unknown source/completeness), distinct from explicit `0` values (unknown is NOT zero).
    - Provider totals vs detail: `InputTokens` and `OutputTokens` are totals; `CachedTokens` and `ReasoningTokens` are details and must not be double-added into totals.
    - Failed/interrupted streams retain observed usage on terminal frames/attempt records without concealing the failure.
  - Replay safety and post-commit failure handling:
    - Core executes exactly one attempt per Execute call; no hidden replay or automatic cross-account fallback occurs in M2 even if `Retryable == true` or `RetryDisposition == RetrySafe`.
    - When failure occurs after commit (`Head` handed off, `Committed == true`), attempt terminates with failure and no fallback or body replacement occurs.
    - Ambiguous transport disconnects (e.g. mid-stream drop) have `RetryDisposition != RetrySafe`.
    - Diagnostic detail (`Provider`, `OriginalError`) remains separate and sanitized, never exposed in client-facing `Message`.
- Explicit limits:
  - Do not implement automatic fallback policy, multi-target failover, or retry loops (M3).
  - Do not implement SQLite usage persistence or quota reservation (M3).
  - Do not implement cancellation/partial-close teardown (M2-027) or bounded backpressure (M2-028).
  - Synthetic local fixtures only (`fakeupstream` and `scripted`); no live credentials or external network access.

## Acceptance

- [x] Pre-Head failures return a classified `GatewayError` without stream frames; Core records an uncommitted attempt (`Committed == false`, `Outcome == OutcomeFailed` or `OutcomeCancelled`) exactly once.
- [x] Upstream rejections (HTTP 4xx/5xx) and HTTP 200 declared failures (`status: "failed"`) preserve opaque error body bytes; HTTP 200 status alone never yields `OutcomeSucceeded`; terminal Complete outcome is `OutcomeFailed` with classified `GatewayError`.
- [x] Rate limits (429) and unavailable (503) rejections populate `Retryable == true` and parsed `RetryAfter`, with `RetryDisposition` remaining non-safe (`RetryUnknown` / `RetryUnsafe`); non-retryable rejections (400/401/403) set `Retryable == false`.
- [x] Usage accounting preserves nullable counters (`nil` is not zero), treats `InputTokens`/`OutputTokens` as totals without double-adding `CachedTokens`/`ReasoningTokens`, distinguishes `UsageProvider` vs `UsageUnknown`, and retains observed usage on failed or interrupted attempts.
- [x] Post-commit and ambiguous failures (`Committed == true`) never trigger replay or response body replacement; exactly one attempt is executed and recorded; diagnostic fields (`Provider`, `OriginalError`) remain sanitized and separate from client-safe `Message`.
