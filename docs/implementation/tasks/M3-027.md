# M3-027 — Wire admission and durable accounting into dispatch

## Outcome

Wire token usage estimation, atomic request/attempt admission, durable dispatch-intent gating, and terminal reservation settlement into Core dispatch execution. This is one bounded deliverable in the [M3 registry](../TASKS.md#m3--access-accounts-and-accounting) toward [M3](../ROADMAP.md#m3--access-accounts-and-accounting).

## Scope

- Introduce pure Core accounting abstractions for admission and attempt finalization/settlement, keeping concrete storage implementations decoupled from Core.
- Integrate `ResolveEstimate` (M3-023), admission and token reservation (M3-024), `ExecuteAfterDispatchIntent` (M3-025), and terminal attempt reconciliation/finalization (M3-026) into `Dispatcher.Execute` and `attemptStream`.
- Retain Complete-to-EOF validation and exactly-once arbitration: pre-Head errors, stream close/EOF, cancellations, and trailing-frame violations each produce exactly one terminal finalization and reservation settlement.
- Keep SQL operations strictly outside chunk streaming and network waits: admission and intent gate upstream execution before dispatch; finalization settles after stream close or error.
- Preserve legacy M1 target path without persistent accounting when unconfigured.
- Exclude storage fault recovery policies and fallback retries (reserved for M3-028 and M3-037+) and full daemon startup composition (M3-030).

## Acceptance

- [x] No protected upstream attempt executes before budget estimation, atomic admission, and durable dispatch-intent are recorded.
- [x] Success, pre-Head execution error, streaming cancellation, and trailing-frame violation each finalize the attempt and reconcile the reservation exactly once.
- [x] Streaming delivery remains incremental and opaque with zero SQL operations during active frame reads.
- [x] Core remains free of concrete storage or driver package imports, and non-authoritative observation sinks (`TryRecord`) remain decoupled from authoritative settlement.

## Completion Evidence

Implemented Core-owned `AccountingStore` values and protected `Dispatcher` wiring: selected-Connector `ResolveEstimate` runs before SQLite admission, `ExecuteAfterDispatchIntent` gates Execute, and Complete-to-EOF/Close arbitration invokes durable finalization once. SQLite is adapted only in `cmd/gateway`; `TryRecord` remains observational. Dispatcher tests prove success ordering and opaque body forwarding, no storage calls during Head/Body frame handling, no Execute/finalization after failed admission, no Execute after intent-write failure or pre-intent cancellation, and exactly-once pre-Head, cancellation, and trailing-frame terminal outcomes. The file-backed protected handler test verifies a pre-Head Connector error leaves a durable failed attempt, intent timestamp, and conservative reservation. Integration exposed that SQLite key verification supplied display `key_id` where the ledger requires the internal virtual-key row `id`; `VirtualKeys.Verify` now supplies that internal ID as specified by `TrustedPrincipal`.

RPM/TPM limit rejection now has a distinct SQLite sentinel that also preserves legacy `ErrLedgerConflict` matching. Composition translates only that sentinel to Core's admission-limit sentinel; Core maps only the typed sentinel to `rate_limited`. Stale authorization and other ledger conflicts remain non-rate-limit failures. [M3-RUNTIME](../M3-RUNTIME.md#admission-and-accounting-operations) now explicitly records this classification boundary; the v1 category is already defined in [CONTRACT](../CONTRACT.md#error-model).
