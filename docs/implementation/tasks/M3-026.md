# M3-026 — Reconcile terminal usage and reservations once

## Outcome

Atomically reconcile terminal attempt usage and token reservations in a single SQLite transaction, replacing held reservations with effective charges (or releasing undispatched reservations) by attempt ID and recording `reconciled_at` timestamps for rolling TPM window accounting. This is one bounded deliverable in the [M3 registry](../TASKS.md#m3--access-accounts-and-accounting) toward [M3](../ROADMAP.md#m3--access-accounts-and-accounting).

## Scope

- In `internal/storage/sqlite`:
  - Enhance `Ledger.FinalizeAttempt` to atomically reconcile the attempt's reservation under the existing `BEGIN IMMEDIATE` transaction:
    - Proven undispatched attempts (`state = 'reserved'` transitioning to terminal state): release reservation with `state = 'released'`, `actual_tokens = NULL`, `effective_charge = 0`.
    - Dispatched attempts (`state = 'intent'` transitioning to terminal state):
      - If usage completeness is `complete` and both input and output token counts are present (non-nil and non-negative): record `state = 'settled'`, `actual_tokens = input + output`, `effective_charge = input + output` (including overage where `actual > estimated`).
      - If usage is partial, unknown, or missing counters: record `state = 'conservative'`, `actual_tokens = NULL`, and `effective_charge = max(estimated, lower_bound)` where lower bound is the sum of available non-negative input/output tokens via checked addition.
    - Set `reconciled_at` inside the transaction using UTC Unix milliseconds sampled after acquiring the SQLite writer lock.
    - Guarantee idempotency: identical duplicate `FinalizeAttempt` calls (matching attempt state, terminal metadata, usage counters, and reconciliation outcome) return `nil` without altering counters or `reconciled_at`; conflicting terminal reports return `ErrLedgerConflict`.
  - Extend `ReservationRecord` and provide `Ledger.GetReservation(ctx context.Context, attemptID string) (ReservationRecord, error)` to read reservation state (`AttemptID`, `EstimatedTokens`, `ActualTokens`, `EffectiveCharge`, `State`, `ReconciledAt`).
- In `internal/core`:
  - Ensure compatibility with `core.EffectiveTokenCharge(estimate int64, usage *UsageReport, dispatched bool)` so storage reconciliation and core arithmetic remain synchronized.
- Explicit limits:
  - Does not wire end-to-end admission, fallback routing, and reconciliation into `Dispatcher.Execute` or HTTP handlers (reserved for [M3-027](M3-027.md)).
  - Does not implement startup recovery scan / sweep (reserved for [M3-029](M3-029.md)).
  - Does not add cost or pricing engines; charges are billable input + output tokens.

## Acceptance

- [x] Undispatched attempts (`reserved`) transitioned to a terminal state atomically set reservation `state = 'released'`, `actual_tokens = NULL`, `effective_charge = 0`, and set `reconciled_at`.
- [x] Dispatched attempts (`intent`) with complete provider input and output counts set reservation `state = 'settled'`, `actual_tokens = input + output`, and `effective_charge = input + output`; actual overage above estimate is fully charged and not truncated.
- [x] Dispatched attempts (`intent`) with partial, missing, or unknown counters set reservation `state = 'conservative'`, `actual_tokens = NULL`, and `effective_charge = max(estimated, lower_bound)`; reasoning and cached detail tokens are stored in `usage_records` but never added to the effective charge.
- [x] Duplicate completion, Close/cancel races, and repeated settlement on the same attempt ID are idempotent no-ops and cannot change totals twice; conflicting terminal outcomes return `ErrLedgerConflict`.
- [x] Transaction failure leaves the attempt and held reservation unmutated and recoverable.
