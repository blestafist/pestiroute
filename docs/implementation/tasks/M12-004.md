# M12-004 — Implement overview usage routing and diagnostics screens

## Outcome

Deliver interactive overview, usage ledger, routing topology, and settings/diagnostics screens on the frontend fixture adapter. Includes nullable ledger metrics (unknown vs zero), paginated request history with attempt and fallback outcome detail, configuration-backed routing topology with declared capability constraints, and read-only settings/diagnostics with safe correlation IDs and cache clearing. Completes the remaining operator UI screens for [M12-WEBUI](../M12-WEBUI.md) tracked in [TASKS](../TASKS.md#m12--webui).

## Scope

- `web/src/fixtures.ts`:
  - Extend fixture models with structured request ledger entries (request ID, timestamp, route/model alias, status/outcome, attempt count, fallback decision, nullable input/output tokens with explicit `null` for unknown), routing definitions (model alias, protocol, connector/account target, declared capability status: `supported`, `unsupported`, `unknown`), and runtime settings/diagnostics (gateway version, component readiness, endpoint URLs, safe correlation ID, restart-required indicators).
  - Add query/filtering helpers for time window, model, and outcome status, along with synthetic pagination (page navigation and sizing).
- `web/src/App.tsx` (and/or dedicated subcomponents in `web/src/`):
  - Overview screen (`/`): Summary cards displaying gateway readiness, enabled account count, and recent ledger request volume; unknown counts explicitly render as `Unknown` rather than `0`; recent request/error activity list linking directly to Usage; component readiness summary; no provider quota or live provider health claims.
  - Usage screen (`/usage`): Filterable request table (filters: model alias, outcome status); pagination controls preserving active filters; filter modifications resetting pagination to page 1; nullable token metrics displaying `Unknown` when `null` (never coerced to `0`); expandable request row or detail drawer displaying attempt breakdowns, selected target account/route, error reason, and fallback decision; no body or prompt inspection affordance.
  - Routing screen (`/routing`): Read-only routing topology grouped by protocol/model alias and target account/connector; declared capability constraints rendered with tri-state badges (`supported`, `unsupported`, `unknown`); persistent banner/notice that topology is configuration-backed and modifications require restart; navigation links to Connections and Usage.
  - Settings & Diagnostics screen (`/settings`): Gateway version, component readiness table, non-secret endpoints, runtime settings, and restart-required badges; safe diagnostic correlation ID copy action; explicit session logout clearing in-memory token and sensitive view cache; zero exposure of operator tokens, credentials, or prompt bodies.
  - Screen state handling: Loading skeletons/indicators, empty results explaining active filters, disconnected notice preserving filters, and partial data rendering where individual unavailable fields are labeled unknown.
- `web/src/App.test.tsx` (and/or additional test files in `web/src/`): Component tests covering overview metrics rendering (null vs zero), usage filtering and pagination, request detail/fallback outcome display, routing topology and capability badge rendering, settings/diagnostics display, and safe logout/cache clearing.
- Out of scope: Live M11 admin API integration (deferred to M12-005); Go embed packaging and full operator E2E (deferred to M12-006); prompt or body payload inspection; route mutation or hot reload.
