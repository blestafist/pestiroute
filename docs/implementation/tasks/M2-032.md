# M2-032 — Enforce provider-agnostic Core and registry dependencies

## Outcome

The architectural boundary separating Core Runtime from concrete Protocol Adapters, Connectors, and protocol parsers is verified reproducibly by automated checks and negative fixtures rather than informal convention. See [registry](../TASKS.md#m2--connector-api-and-conformance-baseline) and [M2](../ROADMAP.md#m2--connector-api-and-conformance-baseline).

## Scope

- In `internal/core` (e.g. `internal/core/dependencies_test.go` or `scripts/check.sh`):
  - Add an automated import and dependency check inspecting production Go package metadata for `internal/core`.
  - Assert that production `internal/core` imports only permitted standard library packages and zero concrete adapters (`internal/adapter/...`), connectors (`internal/connector/...`), test fixtures (`internal/testutil/...`), or foreign packages.
  - Distinguish production package imports from test-only imports (`TestImports` / `XTestImports`).
  - Add a negative test fixture / simulated package input verifying that an illegal adapter/connector import is explicitly detected and rejected.
  - Guardrail verification confirming `internal/core` contains no provider-name branching (`openai`, `anthropic`, etc.) or universal LLM structures (`Message[]`, `Tool[]`, `Reasoning{}`).
- Explicit limits:
  - No generalized external linter frameworks, AST rewrite tooling, or network-dependent linters.
  - Composition root (`cmd/gateway`) remains permitted to import adapters, connectors, and core to wire them together.
  - Local, offline, deterministic execution only.
