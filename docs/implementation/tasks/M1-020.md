# M1-020 — Concurrent isolation and finalization races

## Outcome

Concurrent native requests remain isolated when completion, cancellation and shutdown race. See [registry](../TASKS.md#m1--transparent-responses-proxy-planning-candidates) and [M1](../ROADMAP.md#m1--transparent-responses-proxy).

- [Component descriptor and lifecycle](../CONTRACT.md#component-descriptor-and-lifecycle), [usage and runtime services](../CONTRACT.md#usage-and-scoped-runtime-services).

## Scope

- Add targeted concurrent test scenarios covering competing execution paths:
  1. Competing concurrent requests through `cmd/gateway` and `internal/core` with distinct request bodies, headers, and client streams to prove request isolation and no cross-request state leakage.
  2. One request cancelled while another completes successfully.
  3. Competing terminal signals on an active attempt (client close, upstream complete/EOF, context timeout, and server drain/shutdown) to verify exactly-once `Finalize` execution.
- Fix any exposed races or state sharing in existing dispatch/stream lifecycle without changing the external contract.
- Stop before persistent accounting, multi-target routing, rate limits, account pools, or stress/benchmarking frameworks.

## Acceptance

- [x] Request/attempt IDs are unique and payload bytes/control state never cross requests; cancelling or failing one request does not cancel or corrupt a concurrent request.
- [x] Each attempt finalizes exactly once despite competing Complete, Close, timeout, or shutdown signals (`len(results) == 1` per attempt).
- [x] Interrupted usage remains partial/unknown (`UsageUnknown`); native failure is not overwritten by success; a subsequent request succeeds cleanly on the same gateway instance.

## Completion Evidence

Added deterministic concurrency coverage in `internal/core/dispatch_test.go` and `cmd/gateway/main_test.go`. Core blocks the cancelled request before completion, cancels it, waits for its finalization, then completes the independent request; payload and request/attempt IDs remain isolated. Gated Complete and EOF also race with context deadline and stream Close; every attempt finalizes once. Gateway concurrently sends distinct bodies/headers, cancels one client (asserting `OutcomeCancelled` and upstream cancellation), and proves the other completes. It raises the drain admission guard with both attempts active, verifies a new request is rejected while active work continues, then verifies a subsequent request succeeds after drain ends. Three admitted requests have unique IDs and one finalization each; interrupted usage is unknown. Existing full-suite tests cover shutdown-deadline cancellation and native upstream failure. No runtime change was needed.
