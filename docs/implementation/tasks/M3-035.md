# M3-035 — Coordinate authentication and serialize account refresh

## Outcome

Coordinate authentication and serialize account refresh in the Core runtime. Provide provider-neutral start, continue, and refresh orchestration over the existing v1 Connector `Authenticate` method and scoped runtime services without opening transactions across network boundaries. Ensure per-account concurrency serialization, revision CAS, restart-safe pre-exchange refresh markers, atomic resolution, safe quarantine on failure, and clean isolation across accounts. This is one bounded deliverable in the [M3 registry](../TASKS.md#m3--access-accounts-and-accounting) toward [M3](../ROADMAP.md#m3--access-accounts-and-accounting).

## Scope

- Runtime coordinator in `internal/core/auth_coordinator.go` (and direct tests in `internal/core/auth_coordinator_test.go`):
  - Interface and struct for coordinating auth operations over registered Connectors and scoped runtime services (`InvocationServices`).
  - Interactive session orchestration (`Start` and `Continue`):
    - `Start`: validates account and connector; calls `Authenticate(ctx, AuthRequest{AccountID, Action: "start"}, services)`. If `Supported` and `NextAction == "continue"`, generates unguessable session ID and stores encrypted state envelope with fixed expiry and expected credential revision via `AuthSessions.CreateInteractiveSession`. If flow finishes without continuation (`NextAction == ""`), updates candidate credentials via CAS if returned, without creating a session. If unsupported or error, creates no session and fails closed.
    - `Continue`: resolves active unexpired session via `AuthSessions.GetInteractiveSessionDecrypted`, checks recorded credential revision, decrypts state, and invokes `Authenticate(ctx, AuthRequest{AccountID, Action: "continue", State: state}, services)`. On success with `NextAction == "continue"`, consumes old session and creates next encrypted state (or updates state); if `NextAction == ""`, persists candidate credentials via CAS and consumes session. On cancellation, expired session, stale revision, or error, fails closed and consumes/invalidates session.
  - Per-account refresh serialization & safety (`Refresh`):
    - In-memory per-account locks/coalescing ensuring at most one refresh exchange runs concurrently per account; independent accounts proceed concurrently without lock contention or data sharing.
    - Refresh waiters reload the account's credential revision after acquiring the lock; if the revision already advanced and credentials are valid, skip invocation and return refreshed credentials.
    - Pre-exchange durable refresh marker creation via `AuthSessions.CreateRefreshMarker`. Map raw SQLite unique constraint collisions (`UNIQUE constraint failed: auth_sessions.account_id`) to typed conflict error (`ErrRefreshMarkerConflict`).
    - If preflight check proves invocation was never initiated, clear marker via `AuthSessions.ClearRefreshMarker`.
    - No SQL transaction spans the Connector `Authenticate` call.
    - Atomic credential replacement and marker clearing on success via `AuthSessions.ResolveRefreshAndReplaceCredentials`.
    - Injected or encountered post-exchange persistence failures (or stale revision CAS): preserve/quarantine the marker as `uncertain` (`persistence_failed` or `ambiguous_result`), leave old credentials unchanged, return an authentication persistence failure, and never report false success or repeat the exchange blindly.
    - Connector error, cancellation after call begins, or `Supported: false`: quarantine marker as `uncertain` (`cancelled_after_call` or `ambiguous_result`), fail closed.
  - Address M3-034 integration cautions from owning sources:
    - Map `CreateRefreshMarker` raw SQLite constraint collision to typed conflict handling.
    - Consumed interactive session rows retain historical metadata with cleared envelopes under schema v5 `ON DELETE RESTRICT`; account retention/pruning is an operator lifecycle concern and no retention/product intent is invented.
    - Invalidation behavior per M3-AUTH consumes active sessions and quarantines in-progress refresh as `uncertain`.
- Concrete composition adapter in `cmd/gateway/auth_store.go` between the runtime-owned Core interface and SQLite repositories; Core must not import SQLite. Translate only the auth-session account uniqueness collision to the Core marker-conflict sentinel.
- SQLite-backed atomic repository operations and direct integration tests for encrypted Start/Continue state, session revision CAS/consumption, credential replacement plus marker resolution, stale CAS, quarantine after storage failure, expiry/consumed rejection, and invalidation.
- Explicit limits:
  - Connector invocation, HTTP networking, and OAuth token protocol handling are outside scope (M3-035/M3-036; verified using scripted/fake Connectors).
  - CLI commands (`cmd/gateway` auth CLI) are outside scope (M3-036).
  - No plaintext secrets, tokens, or master keys in database, WAL, errors, or logs.

## Acceptance

- [x] Concurrent same-account refresh calls coalesce/serialize: exactly one Connector `Authenticate` call runs; waiters observe the updated revision without redundant network exchange.
- [x] Concurrent refresh calls for different accounts proceed independently without lock contention or cross-account credential leakage.
- [x] Start and Continue manage interactive session lifecycle: unguessable session IDs, authenticated encryption of opaque state, fixed expiry enforcement, and atomic consumption upon completion or terminal error.
- [x] Stale credential revision rejects continuation and refresh results atomically via CAS, preventing overwrites of externally updated credentials.
- [x] Pre-exchange refresh marker is committed before invocation; preflight cancellation/abort prior to call cleanly clears the marker.
- [x] Cancellation or failure after Connector call begins transitions the refresh marker to `uncertain` quarantine (`cancelled_after_call` or `ambiguous_result`); no SQL transaction spans the Connector call.
- [x] Injected post-exchange credential persistence failure leaves old credentials intact, preserves/quarantines the marker as `uncertain`, returns an authentication persistence error, and does not report false success.
- [x] `CreateRefreshMarker` collisions or constraint failures are mapped to typed conflict errors without leaking unhandled raw SQLite panics/errors.
- [x] Coordinator-to-SQLite adapter integration proves successful refresh replacement and marker clearing, stale CAS without credential mutation, write-failure quarantine, encrypted interactive lifecycle, expiry/consumed rejection, and account invalidation.
- [x] Continue advance and terminal completion are atomic with the expected credential revision; Connector error/unsupported/cancellation quarantine or consume state conservatively, and returned storage/Connector errors cannot disclose secret values.
- [x] Same-account refresh waiters skip the exchange after a valid revision advance; different accounts exchange concurrently. M3-AUTH mandates refresh serialization; Continue additionally serializes by account and reloads its session under lock to prevent duplicate use of stale opaque state. Start remains revision-bound and can race safely through CAS.
- [x] Plaintext credentials, tokens, or master keys are never logged, placed in error strings, or stored unencrypted.
